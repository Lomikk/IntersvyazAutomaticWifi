# IntersvyazAutomaticWifi

Экспериментальный Windows-клиент для автоматизации авторизации в captive portal Wi‑Fi «Интерсвязь» на собственном устройстве и с собственной учётной записью.

## Телеметрия авторизации

C#-клиент поддерживает opt-in local-first телеметрию для измерения реальной гонки `stepOne → concurrent push polls → stepTwo → Internet`. После регистрации приложение один раз спрашивает разрешение на отправку анонимной статистики; при отказе повторного вопроса на обычных запусках нет, а настройку всегда можно изменить через `Настройки → Анонимная статистика`. Пока разрешение не дано, authorization telemetry не записывается в очередь и не отправляется. При включённой статистике во время критического окна никакие telemetry HTTP-запросы не выполняются: миллисекундные события сначала накапливаются в памяти, после завершения сетевой попытки сохраняются в `%LOCALAPPDATA%\IS74Wifi\telemetry\pending`, а фоновый режим отправляет их редкими пакетами только вдали от ближайшего окна авторизации. Сохраняются planned/actual/completed timings, количество одновременно выполнявшихся mailbox GET, факт раннего `stepTwo` и независимое подтверждение Интернета; телефон, Bearer, коды и сырой mailbox JSON в telemetry contract отсутствуют. Подробный контракт: [`docs/telemetry.md`](docs/telemetry.md).

Production HTTPS endpoint Google Apps Script встроен в клиент, поэтому обычному пользователю ничего настраивать не требуется. Для разработки его можно переопределить через `IS74W_TELEMETRY_URL` или `TelemetryEndpoint`; отказ telemetry никогда не блокирует Wi-Fi авторизацию. Локальный замер скорости работает и без согласия на статистику; попытка публикации результата в анонимный рейтинг повторно спрашивает разрешение только если оно ещё не включено.

Для диагностики backend предусмотрена команда `backend-diagnose`: она показывает DNS, каждый redirect Apps Script, финальные status/body/elapsed и затем повторяет GET штатным `TelemetryClient`. Вариант `backend-diagnose --post` дополнительно проверяет `doPost` заведомо невалидным payload без добавления строки в Google Sheets.

## Миграция на C#

Типизированная реализация на C#/.NET 10 дошла до полевого alpha-кандидата. Для C#-кандидатов выбран NativeAOT `win-x64`: после перехода JSON-моделей на source generation пакет проходит `version`/`status` smoke-тесты и остаётся одним самодостаточным `IS74Wifi.exe`. Release workflow прогоняет C# contracts и PowerShell reference regressions, публикует версионированный NativeAOT EXE с SHA-256 и временно сохраняет legacy ZIP для обновления старых клиентов. C#-клиент использует per-user установку рабочей копии в `%LOCALAPPDATA%\Programs\IS74Wifi`, автозапуск с этого стабильного пути и self-update через публичные GitHub Releases (`update-check` / `update`) с обязательной проверкой опубликованного SHA-256 перед заменой EXE. Начиная с alpha.11 установленная копия также регистрируется в стандартном списке приложений Windows и имеет единый полный uninstall flow. Начиная с alpha.12 обычный запуск внешнего EXE сначала предлагает per-user установку, после чего меню всегда работает из канонической копии; установка и автоматическая авторизация больше не являются одним действием. Начиная с alpha.13 интерактивный терминальный интерфейс получил адаптивную двухпанельную компоновку, горячие клавиши и построчную историю многошаговых действий с переносом по фактической ширине панели. Начиная с alpha.14 self-update показывает прогресс скачивания и установки, сохраняет консоль при handoff, повторяет замену EXE при кратковременной блокировке и пытается откатиться на предыдущую копию при сбое. Начиная с alpha.15 фоновый агент поддерживает настраиваемые Windows-уведомления: по умолчанию показываются только важные успешные/ошибочные результаты, а режим `все` дополнительно сообщает о приближении окна и старте автоматической попытки. Данные и DPAPI-секреты остаются отдельно в `%LOCALAPPDATA%\IS74Wifi`. PowerShell-клиент остаётся production/reference реализацией, пока C#-версия не подтвердит поведенческий паритет на Windows 10/11. Рабочая дорожная карта: [`docs/csharp-migration-roadmap.md`](docs/csharp-migration-roadmap.md).

### C# установка и обновление

C#-клиент поставляется одним self-contained EXE. При первом обычном запуске внешняя копия предлагает per-user установку; команда `install` выполняет ту же установку без включения автозапуска. Рабочая копия хранится по стабильному пути:

```text
%LOCALAPPDATA%\Programs\IS74Wifi\IS74Wifi.exe
```

После установки внешний EXE передаёт обычный запуск установленной копии, если установленная версия не старше запущенной. Если внешний EXE новее, он предлагает обновить каноническую копию и только затем открыть меню. Включение автоматической авторизации — отдельное действие: оно создаёт Run-запись и запускает агент, но больше не занимается установкой. Состояние приложения при этом остаётся отдельно в `%LOCALAPPDATA%\IS74Wifi`. Запись `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` указывает только на установленную копию; устаревшая Run-запись с отсутствующим или чужим путём считается битой и очищается при показе состояния. Установка также создаёт per-user запись `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\IS74Wifi`, поэтому IS74Wifi виден в стандартном списке установленных приложений Windows, а системная кнопка удаления вызывает тот же `uninstall` через канонический EXE. Команды `update-check` и `update` читают публичные GitHub Releases без пользовательского токена, выбирают более новую подходящую версию, предпочитают прямой `IS74Wifi-<tag>-win-x64.exe` с соответствующим `.sha256` и умеют откатываться к legacy ZIP для старых переходных релизов. SHA-256 проверяется до запуска и замены установленного EXE; применение выполняет отдельный временный процесс. В `Настройки → Обновления` доступны два режима: `уведомлять` (по умолчанию) и `автоматически`. Проверка выполняется при открытии UI и фоновым режимом не чаще одного раза в шесть часов, а после сетевых ошибок используется backoff. В режиме уведомлений найденная версия показывается в CLI и Windows-уведомлении; нажатие на уведомление открывает раздел обновлений. В автоматическом режиме новая версия скачивается и проверяется только в безопасный момент вне authorization flow, а при открытом UI установка откладывается до выхода. Отдельный переключатель `Pre-release (не рекомендуется)` управляет каналом: alpha-сборки до явного выбора пользователя продолжают видеть prerelease, стабильные сборки по умолчанию — нет. `uninstall` останавливает агент и удаляет Run-запись, локальные данные, запись из Installed Apps и установленную копию; первоначально скачанный EXE вне каталога установки остаётся пользовательским файлом.

Для локальной разработки можно явно отключить перенаправление на каноническую установленную копию, не меняя production-поведение:

```powershell
$env:IS74W_RUN_LOCAL = "1"
.\src\IS74Wifi.App\bin\Debug\net10.0-windows10.0.19041.0\IS74Wifi.exe
```

`IS74W_RUN_LOCAL=1` действует только для текущего процесса/окружения: внешний Debug EXE не предлагает установку поверх уже установленной версии и не передаёт команду в `%LOCALAPPDATA%\Programs\IS74Wifi\IS74Wifi.exe`. Это предназначено только для разработки и ручной проверки локальной сборки. В Visual Studio тот же режим доступен готовым launch-профилем **`IS74Wifi.App (Local Debug)`**: достаточно выбрать его рядом с кнопкой запуска и нажать F5. Обычный профиль `IS74Wifi.App` сохраняет production bootstrap/forwarding.

Обычный C#-запуск использует интерактивный terminal UI: постоянный ASCII-wordmark `IS74W`, слева state-aware меню, справа компактное состояние приложения. Главная страница оставляет только часто используемые действия: ручную авторизацию, автоавторизацию, speed tools, состояние, `Настройки` и `Обслуживание`. Уведомления, политика проверки сети, согласие на анонимную статистику и отдельный раздел `Обновления` вынесены в `Настройки`; регистрация/сброс регистрации, diagnostic log и удаление программы — в `Обслуживание`. Раздел обновлений показывает режим `уведомлять/автоматически`, канал Pre-release, ручную проверку, установку найденной версии и ссылку на изменения. Когда новая версия уже известна, на главной странице дополнительно появляется горячая клавиша `U` без постоянного захламления меню. Взаимоисключающие команды не дублируются: меню показывает либо включение, либо отключение автоавторизации и либо регистрацию, либо её сброс в зависимости от текущего состояния. Многошаговые операции (регистрация, Wi-Fi-авторизация, проверка/установка обновлений и обслуживающие пакетные действия) ведут построчный журнал прямо в левой панели: завершённые этапы остаются видимыми, текущий этап обновляется на месте, а итоговая история остаётся до `Enter`/`Esc` и при необходимости прокручивается. Расширенное техническое состояние открывается как отдельный текстовый отчёт, удобный для копирования, тогда как правая панель остаётся кратким live-status. Стартовый banner проявляется коротким цветовым sweep и затем поднимается в header; любую стартовую анимацию можно пропустить первой клавишей. Пока меню открыто, по banner изредка проходит только мягкий световой sweep без локального мерцания отдельных букв. Для окна меньше примерно `80x30` символов используется то же state-aware клавиатурное меню без полноэкранной композиции. Первый запуск показывает только установку/выход и не открывает остальные действия до создания канонической per-user копии.

Правая панель использует только два маркера состояния: `●` для активного/подтверждённого и `○` для неактивного/неподтверждённого. Сеть и политика её проверки сведены в одну строку: при обычном режиме показывается найденный SSID или `не определена`, а при пользовательском override — `проверка отключена`. По умолчанию авторизация разрешена только при обнаруженном `Campus Wi-Fi*`; в `Настройки → Проверка сети` пользователь может отключить этот gate, после чего ни ручной flow, ни фоновый процесс не используют SSID/тип адаптера как блокирующее условие. Это предназначено для USB-раздачи, VPN/proxy/WARP, нескольких сетевых интерфейсов и другой нестандартной маршрутизации. До первой известной авторизации UI показывает `ещё не выполнялась`; после успешной авторизации — живой отсчёт `до следующей ~HH:MM`, а если портал сообщает, что сеть уже авторизована, но точное начало 24-часового окна неизвестно, показывается `уже активна`. C#-клиент читает только SSID через рекомендованный Windows `WlanConnectionProfileDetails.GetConnectedSsid`; location-gated вызов `WlanQueryInterface(current_connection)` и сбор BSSID удалены. Поэтому сигнал, PHY и link-rate в speed-test telemetry остаются `unknown`, зато штатный C# EXE не должен запрашивать доступ к точному местоположению ради определения сети.

## Production MVP

В репозитории появился первый unattended-клиент под встроенный **Windows PowerShell 5.1**:

- `IS74Wifi.ps1` — CLI/текстовое меню (`register`, `connect`, `status`, `install`, `uninstall`, `reset`, `purge`, `logs`);
- `agent.ps1` — скрытый per-user агент, запускаемый через Task Scheduler при входе пользователя;
- `src/IS74Wifi.psm1` — регистрация, DPAPI-хранилище, captive flow, диагностика и автозапуск.


Tray и Windows Service в MVP не используются. Агент пока работает в интерактивной сессии текущего пользователя, чтобы использовать тот же DPAPI `CurrentUser`-контекст. После запуска агент отсоединяется от console/pseudoconsole через Win32 `FreeConsole`, чтобы Windows Terminal на Windows 11 не оставлял пустое окно для долгоживущего фонового процесса. Фоновый агент может показывать Windows-уведомления о приближении ожидаемого окна авторизации, начале автоматической попытки, успешной авторизации и ошибках. В меню доступны режимы `важные` (по умолчанию), `все` и `выкл`; пока открыт интерактивный IS74Wifi, фоновые уведомления подавляются, чтобы не дублировать видимый TUI. После успешного `POST /stepTwo` сохраняется ожидаемое 24-часовое окно. Вне небольшого guard-window вокруг 24-часовой границы фоновый агент не тестирует Internet и не трогает captive portal. За 10 секунд до ожидаемого expiry он начинает быстрый активный контроль: ранний подтверждённый обрыв сразу разрешает `stepOne`. В сам момент expiry и позже таймер уже достаточен сам по себе — предварительный Internet-probe не выполняется, поэтому машина, которая проспала границу и включилась, например, через 32 часа, сразу начинает `stepOne`.

Автоматический цикл может отправить `stepOne` не более четырёх раз. Одна попытка использует полный быстрый polling-профиль; если свежий код не появился, следующая `stepOne` разрешается после пауз 15, 30 и 60 секунд. После четвёртой отправки автоматические попытки прекращаются до явного действия пользователя. HTTP 401 от API немедленно останавливает цикл как `bearer-invalid` и требует повторной регистрации.

Подробности: [`docs/production-mvp.md`](docs/production-mvp.md).

## Что уже подтверждено экспериментально

1. Windows может самостоятельно пройти телефонную авторизацию API приложения и получить собственный долгоживущий Bearer без Android/эмулятора.
2. Для обычного SMS-подтверждения `POST /mobile/auth/check-confirm` должен получать **пустой `authId`**. Новый `authId`, пригодный для `/mobile/auth/get-token`, приходит уже в ответе `/check-confirm`.
3. Полученный Windows Bearer успешно работает с `GET https://api.is74.ru/mobile/pushmessages`.
4. В тесте сервер выдал сессию сроком на один год (`ACCESS_BEGIN` → `ACCESS_END`).
5. Captive portal подтверждён HAR-трассировкой: `stepOne` → `stepTwo` → `stepThree`. Финальный `stepTwo` содержит только `confirmCode` и `phone`; cookies/CSRF в наблюдавшемся сценарии не требовались.
6. Wi‑Fi-код появляется в серверной ленте `/mobile/pushmessages`, поэтому ежедневная работа не требует Android push.
7. Подходящий постоянный канал для общей ленты кодов (SSE/long-poll/WebSocket) в исследованной реализации не обнаружен. Для MVP используется короткий polling `/mobile/pushmessages`.
8. `page=1&pageSize=1` возвращает самую свежую запись; наблюдавшиеся ID идут от новых к старым. Для свежего чтения используется `Cache-Control: no-cache`, при котором сервер отвечал `X-Cache-Status: BYPASS`.
9. Параллельный замер показал, что новое сообщение с Wi‑Fi-кодом становится доступно практически одновременно с обработкой `/stepOne`: в одном измерении последний GET со старым ID завершился на ~70.6 ms, `/stepOne` вернул `302` на ~135.4 ms, а следующий GET с новым ID завершился на ~139.3 ms относительно начала `/stepOne`.
10. Burst-тест с независимыми GET показал практическую границу запуска примерно между ~78 ms и ~108 ms: GET, стартовавший около 78 ms, ещё увидел старый ID, а GET, стартовавший около 108 ms и более поздние запросы уже увидели новый код. Результат GET, запущенного около `T=0`, не используется как граница, потому что тот запрос завершился аномально поздно.
11. Для рабочего кандидата зафиксирован абсолютный polling-профиль от старта `/stepOne`: `100, 150, 200, 250, 350, 500, 700, 1000, 1400, 2000, 3000, 4500, 6500, 10000 ms`. Следующий GET не ждёт ответа предыдущего; после обнаружения нового кода новые GET больше не запускаются.
12. Windows-сессии можно передать человекочитаемые метаданные через `PUT /mobile/pushtoken/add-with-device-id`: проверено обновление активного устройства до вида `DESKTOP-..., Windows ...` без настоящего push-token.
13. Cached-IP-first был проверен в реальном captive-состоянии на Windows и **не принят в production**. Обычный DNS для `api.is74.ru`/`w.is74.ru` занимал примерно десятки миллисекунд, тогда как один заведомо устаревший cached IP с бюджетом `700 ms` добавил около `700 ms` скрытой задержки до DNS. Production C# использует обычный системный DNS; direct-IP код оставлен только как экспериментальная/диагностическая реализация и не подключён к штатным `HttpClient`.
14. Полный end-to-end тест подтвердил минимальный captive-протокол без промежуточных страниц: `baseline → POST /stepOne → GET /pushmessages → direct POST /stepTwo → Internet`. В успешном запуске код был получен в памяти примерно через `178.4 ms`, `/stepOne` вернул `302 → stepTwo?...` примерно через `207.4 ms`, прямой `POST /stepTwo` без `GET /stepTwo` вернул `302 → stepThree`, а Интернет затем подтвердился без единого `GET /stepThree`. Следовательно, `GET /stepTwo` и `GET /stepThree` рабочему клиенту не требуются.
15. Основной connectivity probe перенесён на локальный `http://online.susu.ru/`. На открытом Интернете он быстро отвечает HTTP-редиректом на `https://online.susu.ru/`; в реальном captive-состоянии на Windows Интерсвязь возвращает `HTTP 200` с небольшим HTML/JS, ведущим на `w.is74.ru`. Production считает Интернет подтверждённым только при `3xx` с точным `Location: https://online.susu.ru/`; body на success-path не читается.

Подробности: [`docs/protocol.md`](docs/protocol.md).

## Структура

- `experiments/01-get-confirm.ps1` — создаёт/переиспользует Windows `deviceId` и запускает телефонное подтверждение.
- `experiments/02-check-confirm.ps1` — проверяет SMS-код; для обычного SMS отправляет пустой `authId` и сохраняет новый подтверждённый `authId`.
- `experiments/03-get-token.ps1` — получает `AuthSession`, сохраняет Bearer через Windows DPAPI и записывает несекретные метаданные сессии.
- `experiments/04-read-pushmessages.ps1` — проверяет чтение `/mobile/pushmessages` с локальным Bearer.
- `experiments/05-register-device-metadata.ps1` — обновляет существующую Windows-сессию человекочитаемыми `DEVICE_MODEL` и `OS_VERS` без поддельного push-token.
- `experiments/06-measure-push-latency.ps1` — запускает наблюдатель `/pushmessages` до `/stepOne` и измеряет момент появления новой записи; код не выводится и `/stepTwo` не вызывается.
- `experiments/07-fast-code-acquisition.ps1` — кандидат рабочего алгоритма: один `/stepOne` и независимые GET `/pushmessages` по абсолютному расписанию; прекращает запуск новых GET после обнаружения свежего кода, не вызывает `/stepTwo` и не печатает код.
- `experiments/08-direct-step-two.ps1` — end-to-end эксперимент: получает свежий код тем же polling-профилем и сразу отправляет прямой `POST /stepTwo`; `GET /stepTwo` и `GET /stepThree` отсутствуют. Успешный запуск подтвердил открытие Интернета.
- `prototypes/01-captive-manual-code.ps1` — прототип штатной длинной последовательности captive portal с ручным вводом 4-значного кода.
- `docs/protocol.md` — зафиксированные параметры протокола и известные неизвестные.

## Локальное состояние

По умолчанию эксперименты используют:

```text
%LOCALAPPDATA%\IS74Wifi\
    device-id.txt
    bearer.dpapi
    session-meta.json
    check-confirm-success.json
    device-metadata.json
```

`bearer.dpapi` создаётся через Windows DPAPI и не должен попадать в репозиторий.

Production-клиент также пишет диагностический журнал в:

```text
%LOCALAPPDATA%\IS74Wifi\logs\diagnostic.log
```

Журнал ротируется при размере около 1 МБ и хранит не более пяти файлов (`diagnostic.log` + `diagnostic.1.log` … `diagnostic.4.log`), то есть занимает примерно до 5 МБ. В нём сохраняются переходы state machine, HTTP-коды, redirect `Location`, серверный `Date`, задержки запросов, номера попыток `stepOne`, ID push-сообщений и причины ошибок. Bearer, полный телефон, SMS-коды, Wi-Fi-коды и request body с секретами намеренно не записываются. Папку журнала можно открыть через `IS74Wifi.ps1 logs` или пункт меню «Открыть диагностические логи».

## Статус

Минимальный рабочий протокол уже подтверждён end-to-end:

```text
обнаружить captive Wi‑Fi
→ прочитать существующий Bearer из DPAPI
→ получить baseline ID верхнего сообщения
→ запустить POST /stepOne в T=0
→ независимо запускать GET /pushmessages по абсолютному расписанию
  100, 150, 200, 250, 350, 500, 700, 1000, 1400, 2000, 3000, 4500, 6500, 10000 ms
→ остановить новые GET сразу после появления свежего Wi‑Fi-кода
→ как только свежий код найден, сразу POST /stepTwo с кодом; browser-facing 302 от /stepOne не является gate
→ если за полный polling schedule кода нет, попытка stepOne считается потраченной и может быть повторена в рамках лимита 4
→ НЕ открывать /stepTwo страницей
→ НЕ открывать /stepThree
→ проверить появление Интернета
```

Если верхнее новое сообщение оказалось не Wi‑Fi-кодом, предусмотрен fallback: один запрос с большим `pageSize` и поиск подходящего сообщения среди `id > baselineId`.

По умолчанию Production MVP требует текущий SSID с префиксом `Campus Wi-Fi`; вне такой сети captive-авторизация не запускается. Пользователь может явно выбрать `Проверка сети: отключена`, и тогда этот gate полностью пропускается как для ручной, так и для автоматической авторизации. После полевого сравнения DNS и direct-IP production C# намеренно использует обычный системный DNS: cached-IP-first давал небольшой выигрыш при актуальном адресе, но создавал значительно больший скрытый штраф при устаревшем. Для определения captive-состояния используется локальный `http://online.susu.ru/` с редиректами отключёнными; Online подтверждается только ожидаемым `3xx → https://online.susu.ru/`.

Регистрация человекочитаемых метаданных Windows-устройства уже проверена отдельно и может быть частью onboarding/первого запуска MVP.

## Безопасность

Не коммитьте Bearer, SMS-коды, HAR-файлы с живыми данными, cookies или локальные файлы `%LOCALAPPDATA%\IS74Wifi`. Репозиторий содержит только воспроизводимую логику и обезличенные параметры протокола.
