## Почему Git показывал 338 исходящих коммитов

Репозиторий был shallow: история новых remote-коммитов обрывалась на `fcd1cf1`.
Из-за этого Git не находил общий предок и показывал 338/16 вместо реального
отставания. `git fetch --unshallow --no-tags origin` восстановил историю:
локальная `main` имеет 0 исходящих и 19 входящих коммитов; общий предок —
`4cacceb`. Alpha.27 есть и в истории `origin/main`, и в опубликованных releases.
Файлы рабочих деревьев этим fetch не изменялись.

## Что действительно отсутствует в тестовых сборках

### 1. Защита состояния авторизации — `86e6354`, PR #36

В нашей ветке `JsonFileStore.Read` превращает ошибку JSON/I/O в `null`, а
`PathAuthorizationStateStore.Load` трактует её как начальное состояние. При
следующей записи можно затереть историю путей, сроки и счётчики. Не используются
`.bak`, строгая проверка чтения и межпроцессная блокировка read-modify-write.

Актуальная база различает отсутствие, повреждение и временную недоступность;
восстанавливает проверенную `.bak` либо прекращает операцию с ошибкой. Она также
атомарно сохраняет предыдущую версию и удаляет backup при reset. Это исправление
нужно перенести целиком вместе с тестами, не подменяя его нашим IP-кешем:
`campus-addresses.json` и состояние авторизации решают разные задачи.

### 2. VPN: бюджет второй captive-пробы — `92d787a`

У нас повторная независимая проверка использует сохранённый guard timeout
(по умолчанию 300 мс). На актуальной базе ей даётся минимум 2 с — столько же,
сколько первой. Отсутствие DNS благодаря IP-first не гарантирует TCP/HTTP за
300 мс. Поэтому автоматический вход под VPN всё ещё может останавливаться до
stepOne. Ручной успех этого сценария не доказывает исправность автоматического.

В upstream есть также диагностические failure/elapsed/budget и регрессии на
успешную/неуспешную вторую пробу. Увеличенный бюджет не отменяет требование двух
независимых captive-ответов. В нашей ветке этих изменений и регрессий нет.

### 3. VPN: повторное разрешение адреса — тот же `92d787a`

Upstream переиспользует `InterfaceDnsResolver` между короткими пробами и включает
gateway/ifIndex в ключ его краткоживущего DNS-кеша. Наш общий `PathAddressBook`
уже решает повторный DNS иначе: IP-кандидаты общие для runner/probe и сохраняются
между процессами. Эту часть нельзя переносить как второй параллельный транспорт.

Усиление ключа `InterfaceDnsResolver` можно сохранить для его собственных вызовов.
Но тесты upstream, использующие старые constructor overrides `NetworkPathProbe`,
нужно адаптировать к общему address book. Persistent IP сервера при DHCP/ifIndex
переиспользуется намеренно; новый сокет обязан получать текущую привязку.
Не следует вводить DNS-refresh persistent-записей при каждом изменении binding.

### 4. Уведомления — `4d89800`, PR #32

Пропущено использование постоянного tray icon для уведомлений вместо отдельных
временных значков. С этим связаны очередь сообщений в tray thread, действие по
нажатию на уведомление об обновлении и fallback при скрытом tray. Наши изменения
эти два App-файла не затрагивали: исправление полностью отсутствует.

## Синтетическое сравнение исполняемого Core

Одноразовый harness запускался с Core нашей проверенной сборки и отдельно
собранным Core точного `origin/main`. Все файлы — в изолированных каталогах
`artifacts/field-test/base-audit`; DNS, probe и авторизация подменены. Рабочие
данные, реестр, адаптеры и live-авторизация не изменялись.

| Сценарий | Наша ветка | `origin/main` |
|---|---|---|
| Backup после последовательных записей | Не создан | Создан |
| Срок после повреждения основного JSON | Не восстановлен | Восстановлен |
| Повреждение без backup | Возвращается начальное состояние | Явная ошибка |
| Чтение эксклюзивно заблокированного файла | Возвращается начальное состояние | Явная ошибка |
| DNS-вызовы: исходный binding, другой gateway, другой ifIndex | 1 | 3 |
| Бюджеты первой/второй captive-пробы | 2000/300 мс | 2000/2000 мс |

Строка DNS проверяет именно `InterfaceDnsResolver`, а не persistent IP-кеш.
Сценарий probe проверяет переданный coordinator бюджет, не реальное время сети.
Это диагностика известных пропусков, не полный выпускной или полевой прогон.
Наш старый suite проходил, потому что соответствующие upstream-регрессии также
оставались за пределами локальной базы.

## Объединение и следующие действия

`git merge-tree --write-tree --name-only HEAD origin/main` проверил объединение
без изменения HEAD/index/рабочих файлов. Явные конфликты: `README.md`,
`docs/direct-network.md`, `src/IS74Wifi.Core/NetworkPath.cs`. Автоматически
объединённый текст не доказывает совместимость: старые probe-тесты требуют
адаптации конструкторов и сохранения смысла обеих политик кеширования.

Основную `main` можно обновить fast-forward на 19 коммитов. Это не обновит нашу
отдельную ветку. Для неё требуется интеграция с актуальной `origin/main`, ручное
разрешение пересечений и Full с явным server path, затем NativeAOT и полевые
проверки. Тестовые EXE 1–4 нельзя считать полной заменой актуальной базы.
В рамках аудита ветки не объединялись, исходники не исправлялись и новые EXE не
устанавливались. Ранее известная ошибка backend ingestion остаётся отдельным
ограничением; Full для документационного аудита заново не запускался.
