# Офлайн-реконструкция SMS polling (16.10.2026)

> Исследование для [issue #28](https://github.com/Lomikk/IntersvyazAutomaticWifi/issues/28), без запросов к SMS API и без изменения production-авторизации. Это **сценарная модель**, а не A/B-эксперимент.

## Источник данных

Прочитаны live-листы [IS74Wifi Telemetry](https://docs.google.com/spreadsheets/d/1faOzohjH9zNgfL4FFlyz1kaTCkmYr47SNuDHn9S9lck/edit): `Attempts` и `MailboxPolls`. Повторяющиеся строки удалены по `event_id`. Всего прочитано 243 уникальные записи попыток и 195 уникальных опросов; для количественной модели пригодны **45 успешных авторизаций с полными таймингами и подтверждённым SMS GET, вернувшим код**.

В этой выборке 176 зарегистрированных опросов и 33 HTTP 429; это *подвыборка*, не все 195 уникальных опросов. 32 из 45 запросов, нашедших код, стартовали до ответа `stepOne`; 29 стартовали до, но завершились после. Код был получен раньше `stepOne` лишь в 3 случаях.

## Режимы

- **parallel**: production расписание `[100,150,200,250,350,500,700,1000,1400,2000,3000,4500,6500,10000]` мс от `stepOne`; допускает перекрытие.
- **sequential**: первый SMS GET сразу после завершения `stepOne`, далее без перекрытия, каждые `max(200 мс, наблюдаемый RTT)`.
- **hybrid**: первый GET при завершении `stepOne` или после 250 мс, если ответ ещё не пришёл; далее такой же последовательный опрос.

Во всех трёх сценариях `stepTwo` отправляется сразу после появления кода; ожидание HTTP 302 не добавляется **после** получения кода. Моделируется именно расписание SMS GET, а не изменение момента запуска `stepOne`.

## Что модель должна предположить

В телеметрии не видно точного момента, когда SMS-код появился в серверном ящике. Поэтому модель рассматривает три момента доступности кода **в пределах GET, реально вернувшего его**: начало, середина и завершение запроса. Для каждого прогона используется медианный длительность успешного SMS GET той же попытки (в пределах 15–600 мс). Условно считается, что ответ зависит от содержимого ящика в середине GET.

**HTTP 429 для альтернативного расписания НЕ моделируется.** Неизвестно, какой ответ API дал бы на неотправленный GET и как изменился бы лимитер при другой частоте.

## Результат

| Предположение о готовности кода | Базовая модель parallel: медианная ошибка относительно реальной записи | sequential: медиана разницы с parallel | sequential: p95 разницы | GET меньше, медиана | hybrid: медиана разницы | hybrid: p95 разницы |
|---|---:|---:|---:|---:|---:|---:|
| Начало GET | −5,9 мс | +38,9 мс | +150,8 мс | 2 | +41,1 мс | +150,0 мс |
| 25% длительности GET | −3,6 мс | +36,4 мс | +149,7 мс | 2 | +39,4 мс | +100,8 мс |
| Середина GET | +42,5 мс | −11,1 мс | +152,4 мс | 3 | −11,1 мс | +150,0 мс |
| Завершение GET | +50,6 мс | −5,6 мс | +174,1 мс | 2 | 0 мс | +174,1 мс |

Положительная разница = альтернатива медленнее. Отрицательная = быстрее.

**Важнейшая проверка качества:** при предположениях «середина/конец GET» модель уже плохо восстанавливает фактическую скорость parallel (p95 ошибки модели — приблизительно 399–442 мс, отдельные ошибки — более 1 секунды). Поэтому нельзя использовать их отрицательные результаты как доказательство, что sequential быстрее. «Начало / 25%» лучше воспроизводят медиану, но и они не доказывают реальный выигрыш.

При предположении «25% длительности GET» модель предсказывает, что последовательная стратегия замедлит обнаружение кода на медианные **36 мс** (p95 **150 мс**), но сэкономит медианные **2 SMS GET**. Для гибридной стратегии это **39 мс**, p95 **101 мс**, и также медианные 2 GET.

## Ограничения и решение

Это не прямая оценка процента HTTP 429 после переключения: такие числа можно измерить только в контролируемом полевом сравнении. Нельзя считать HTTP 302 гарантией, что код уже готов к чтению.

Предложение: сохранить production scheduler неизменным до отдельного полевого теста (A/B на естественных повторных авторизациях), собирать p50/p95 полного времени до подтверждённого Интернета, GET/авторизацию, HTTP429/авторизацию и результат `stepOne`. Если менять `stepOne` по 24-часовому таймеру — делать это **отдельным экспериментом**, иначе эффекты смешаются.

## Воспроизведение

На авторизованном тестовом ПК в `%LOCALAPPDATA%\Temp\IS74WifiOfflineReplay` создан обезличенный `sanitized_traces.json` (без `install_id`, `attempt_id`, IP, телефона, кода и текста SMS).

```powershell
node scripts/offline_sms_replay.cjs --self-test
node scripts/offline_sms_replay.cjs "$env:LOCALAPPDATA\Temp\IS74WifiOfflineReplay\sanitized_traces.json" > replay_result.json
```

Скрипт не содержит HTTP-клиента, читает только локальный JSON и выводит JSON-отчёт. Обезличенные тайминги намеренно **не коммитятся** в публичный репозиторий. Запуск на другом компьютере требует собственного экспортированного входного JSON с массивом `attempts`, содержащим `step_one_ms`, `code_observed_ms`, `polls` (`started_ms`, `completed_ms`, `status`, `found`, `index`).
