# Как объяснить проверки сети по журналу

В campus-test.8 причины проб добавлены в локальный `logs/diagnostic.log`.
В campus-test.9 Windows-события дополнительно фильтруются по состоянию выбранных
путей. Интервалы авторизации/повторов, IP-first, telemetry wire и формат сохранённого
состояния не изменены. Новый периодический опрос не добавлен.

В CLI `Unreachable` подписан «сбой проверки», ожидание события — «по событию».
Это не утверждение об отсутствии всего Интернета. TXT поясняет, что HTTP-ответ
не получен, а при event-driven режиме периодическая проверка не назначена.
Столбцы CLI учитывают длину новых подписей в окнах от 80 столбцов.

## Значимые изменения выбранных путей

- `agent.worker start ... version=...`: версия фактически работающего worker,
  PID присутствует в каждой строке. Запущенное меню и установленный worker могут
  принадлежать разным сборкам; по версии/PID видно, откуда получены сведения.
- `agent.selected-profile changed adapter=... previous=... current=... trigger=...`:
  изменился уровень Windows-профиля **выбранного физического адаптера**, а не глобальный
  доступ компьютера через VPN. `trigger` сохраняет источники уведомлений, когда изменение
  действительно принято. WinRT levels: 0=None, 1=LocalAccess, 2=ConstrainedInternetAccess,
  3=InternetAccess; -1 — профиль отсутствует, unknown — не удалось прочитать Windows.
- `agent.selected-profile baseline-check`: при старте физический профиль не подтверждает
  InternetAccess либо неизвестен; однократная синхронизация не доверяет старому Internet
  в сохранённом состоянии, даже если VPN даёт глобальный InternetAccess.
- `agent.selected-path removed`: выбранный активный путь исчез; состояние отключения
  сохраняется, HTTP по отсутствующему пути не выполняется.

В test.9 сырые `agent.event`, `agent.wake`, `agent.wait`, глобальные NCSI transitions
и IPC-complete не записываются. Это записи только старой test.8. Отброшенные события
не создают отдельных строк и сводок. Остаются действия, ошибки и принятые изменения.

Windows-событие будит **локальную сверку**, без HTTP. Координатор сравнивает выбранные
SSID/interface/source IPv4/gateway с сохранённым binding и уровни профилей с предыдущим
снимком в памяти. Повторный callback во время запроса на следующем tick видит тот же
снимок и не вызывает второй HTTP. Изменения VPN/постороннего USB/IPv6-адресов, не изменившие
выбранный путь или уровень его профиля, отбрасываются. Добавленного debounce-таймера нет.

Потеря InternetAccess на выбранном адаптере значима **даже с теми же IP/SSID** и даже
до известного срока авторизации; она приводит к probe и прежнему captive-confirmation,
а не к безусловной авторизации. Resume, StartupOffline, IpcCaptiveRefresh остаются
явными поводами синхронизации untimed путей. Таймеры, ручные запросы и binding changes
сохраняют свои поводы. Критический timer shot проверяется до чтения профилей Windows.

При ошибке чтения профилей unknown отличается от отсутствующего профиля. Переход
в unknown и восстановление дают по одной сверке, повторяющийся unknown не создаёт
HTTP-цикла. Если срок неизвестен и Windows не сообщает **ни одного значимого изменения**,
потеря доступа может остаться незамеченной до ручной проверки/resume. Резервного опроса
по-прежнему нет: это ограничение нельзя устранить одним фильтром уведомлений.

События Windows относятся к компьютеру в целом: callback изменения адресов сам
не сообщает, какой адаптер изменился. Событие на виртуальном/USB-интерфейсе тоже
может разбудить проверку выбранного Wi-Fi. Нельзя называть это переподключением
Wi-Fi без соответствующих данных WLAN журнала Windows.

## Причины реальных проверок

Каждая проверка `NetworkPathProbe` (координатор и IPC diagnostics) получает
`network.probe start id=N ...` и `result id=N ...`, либо `aborted id=N ...`.
Идентификатор уникален внутри процесса; сопоставлять вместе с PID.

| reason | Что произошло |
|---|---|
| `binding.appeared` / `binding.reappeared` / `binding.changed` | Новый/возвращённый путь или изменение transport snapshot |
| `selected-profile.changed` | Изменился уровень выбранного физического профиля, включая неизвестность/восстановление или начальный неполный доступ |
| `event.Resume`, `event.StartupOffline` и др. | Явная синхронизация untimed пути; причины, накопленные до tick, объединены через `+` |
| `scheduled_recheck` | Проверка по существующему расписанию |
| суффикс `.settling-retry` | Уже существовавший однократный повтор после неуспеха при появлении/изменении пути |
| `captive-confirmation` | Обязательная вторая независимая проба перед автоматической авторизацией |
| `pre-step-failure` | Уже существовавшая проверка после отказа до stepOne |
| `ipc.refresh` | Явное обновление статуса через агент, например при открытии меню |
| `ipc.probe-only` | Диагностика/TXT без разрешения на автоавторизацию |
| `event.IpcCaptiveRefresh` | Явный refresh обнаружил captive и передал решение об авторизации координатору |

`start` содержит adapter ID, ifIndex, source IPv4/gateway, фиксированную контрольную
цель и бюджет. `result` — статус, `failure` (например Timeout, ConnectionFailure,
DnsUnavailable, DirectRouteUnavailable), HTTP status, общую и транспортную длительность.
`aborted` сохраняет тип исключения и длительность, после чего прежнее исключение
передаётся вызывающему коду; ошибки не подменяются успешным статусом.

Для прямого TCP-соединения **этих проб** дополнительно пишется `network.probe-tcp`:
фактический IP/порт назначения, ifIndex, источник адреса, признак кеша, результат
соединения либо Winsock-код и длительность. TCP-записи находятся между start/result
того же процесса; операции агента сериализованы существующими gates. Одно HTTP
обращение может перебрать несколько сохранённых IP. Адрес не обновляется через DNS
после ошибки. Эти TCP-записи не подключены к критическому транспорту авторизации.

Более общий HTTP-лог и записи authorization flow остаются прежними; `network.probe`
не является новым трассировщиком всех HTTP-запросов приложения. Не записываются
тела ответов, заголовки авторизации, полный URL, телефон, код или bearer.
Новые записи не отправляются в анонимную статистику. Ротация журнала остаётся прежней.

В test.10 `network.address source=persistent-other-path host=... ifIndex=... candidates=N`
означает, что собственных IP у пути нет и выбраны сохранённые адреса того же сервера
из других путей. Это не смена адаптера: TCP остаётся привязанным к текущему пути.
Для probes фактическое назначение видно в `network.probe-tcp`; источник остаётся
`PersistentAddress`. При обычном переиспользовании кандидатов в памяти отдельной
строки выбора нет. На диск новый путь попадает только после успешного TCP connect;
это не результат авторизации и не доказательство подлинности HTTP-портала.

## Как считать частоту и парные пробы

Считать **start**, а не суммарное число start/TCP/result/старых `agent.path-probe`.
Для соседних start сопоставить PID, adapter, reason и предыдущий result:
так можно отличить повтор, captive confirmation, второй IPC и два события Windows.
В старой test.8 серия `wake` без `network.probe start` означает, что агент проснулся,
но запрос не делал; в test.9 такие локальные сверки не засоряют обычный журнал.

В прочитанном отрезке старого журнала одного worker за примерно 26,5 минуты были
53 строки `agent.path-probe`, из них 25 соседних интервалов короче секунды; минимум
около 0,385 с, максимум около 224,6 с. Частые/парные наблюдения подтверждены, однако
старый формат не позволяет достоверно восстановить их источники. Наличие пар само
по себе не доказывает ошибку scheduler. В следующем наблюдении test.8 за примерно
17 минут найдено 32 пробы: 1 ipc.refresh и 31 event.WindowsAddress. Все получили
HTTP 302 по сохранённому IP; binding Wi-Fi оставался прежним. Парные callbacks,
второй из которых приходил уже во время первого tick, создавали два запроса.
Именно этот случай закрывает фильтр выбранных путей в test.9. Причина генерации
самих адресных уведомлений внутри Windows не установлена.

## Проверка изменений

Контракты подменяют сеть: coalesced WindowsAddress+Resume даёт ровно одну пробу;
untimed отказ не создаёт опрос/таймер/авторизацию, следующее событие даёт следующую
пробу. Проверяются причины, бюджет/длительность/timeout, парные start/result,
сохранность секретов, TCP cached-IP/ConnectionRefused и прежнее число dial attempts.
UI-контракты проверяют подписи и ширину столбцов 80/100/120.
Новые контракты подают серию из 20 неизменившихся уведомлений с изменениями VPN:
ноль HTTP/строк журнала. Проверены поздний дубль во время запроса, selected-only
probe, потеря/восстановление профиля при том же IP, DHCP, удаление/возврат адаптера,
unknown/recovery, resume, сохранение срока и авторизация после двух captive-проб,
а также запуск с уже ограниченным физическим профилем при старом Internet state.

Full Release подтвердил весь клиентский набор и leaderboard backend; известная
серверная ошибка ingestion на строке 142 (`2 != 0`) осталась. Следующий серверный
update-manifest контракт выполнен отдельно и прошёл. Сервер не менялся.

Уточнение 2026-11-03: требование ingestion-теста о постоянной дедупликации после
очистки кеша заменено согласованным контрактом append-only телеметрии: кеш подавляет
недавние повторы, последующие дубли сохраняют `event_id` для удаления при анализе.
Прежний отказ `2 != 0` относился к несовпадению ожидания теста с этим контрактом,
а не к отказу авторизации. Код сервера и клиента при уточнении не менялся.
После уточнения сценарии ingestion до проверки поддержки проекта проходят, однако
Backend с локальным сервером `70ec870` останавливается позже: `GET route=config`
возвращает `invalid_route`, тогда как клиент/тест ожидают `support_url`. Этого
маршрута в локальном `Code.gs` нет. Leaderboard и отдельно выполненный update-manifest
прошли; весь Backend/Full зелёным не объявляется. Рабочий deployment этим не проверен.
