# Production MVP (Windows PowerShell 5.1)

Целевая версия MVP работает на встроенном Windows PowerShell 5.1 и не требует PowerShell 7, отдельного .NET Runtime или постоянной иконки в tray.

## Компоненты

- `IS74Wifi.ps1` — CLI и интерактивное меню.
- `agent.ps1` — фоновый пользовательский агент.
- `src/IS74Wifi.psm1` — HTTP, регистрация, DPAPI, captive portal, диагностика и Task Scheduler.
- `experiments/*` — остаются неизменёнными как воспроизводимые исследования протокола.

## Первый запуск

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\IS74Wifi.ps1 register
```

Пользователь один раз вводит номер телефона и затем SMS-код. После успешного `/get-token` приложение сохраняет номер и Bearer в одном DPAPI-зашифрованном файле текущего Windows-пользователя:

```text
%LOCALAPPDATA%\IS74Wifi\secrets.dpapi
```

`deviceId`, несекретные метаданные API-сессии, runtime-state и журналы хранятся отдельно в той же папке. Промежуточный `authId` на диск не записывается.

Проверенный backend-вариант `addresses=[]` поддерживается полностью. Если `/check-confirm` вернул непустой `addresses`, MVP останавливает регистрацию до выбора `userId`, потому что этот вариант ещё не зафиксирован экспериментально достаточно точно.

## CLI

```text
.\IS74Wifi.ps1 register
.\IS74Wifi.ps1 connect
.\IS74Wifi.ps1 status
.\IS74Wifi.ps1 install
.\IS74Wifi.ps1 uninstall
.\IS74Wifi.ps1 reset
.\IS74Wifi.ps1 purge
.\IS74Wifi.ps1 logs
```

Без аргументов открывается текстовое меню.

## Автозапуск

`install` создаёт задачу `IS74WifiAgent` в Task Scheduler для текущего пользователя и запускает её с `LogonType=Interactive` и `RunLevel=Limited`.

Агент запускается скрыто:

```text
powershell.exe -NoProfile -ExecutionPolicy Bypass -WindowStyle Hidden -File agent.ps1
```

После импорта модуля `agent.ps1` вызывает Win32 `FreeConsole()` и отсоединяет долгоживущий процесс от console/pseudoconsole. Это сохраняет сам `powershell.exe` под управлением Task Scheduler, но не оставляет пустую вкладку Windows Terminal на Windows 11.

Windows Service пока не используется. Это сохраняет текущий пользовательский DPAPI `CurrentUser`-контекст без смены модели хранения секретов.

`uninstall` останавливает и удаляет задачу `IS74WifiAgent` и удаляет `%LOCALAPPDATA%\IS74Wifi`; после этого папку с распакованными файлами программы можно удалить вручную. Пункт «Отключить автозапуск» удаляет только задачу и оставляет регистрацию. `reset` удаляет регистрацию и deviceId. `purge` сохранён как CLI-алиас полной очистки.

## 24-часовой цикл

24-часовая граница считается от успешного `POST /stepTwo → 302 stepThree`. Если ответ `stepTwo` содержит серверный HTTP `Date`, он используется как опорное время; иначе берётся локальный UTC в момент ответа. Ручная неудачная попытка, `stepOne`, получение кода и проверка Internet не сдвигают эту границу.

Вне короткого guard-window вокруг `expectedExpiryUtc` агент не тестирует Internet и не начинает captive-авторизацию. Guard-window начинается за 10 секунд до ожидаемой границы. Внутри предграничной части агент делает быстрые активные Internet-probe; два близких неуспеха означают, что фактическое отключение произошло немного раньше прогноза, и `stepOne` отправляется немедленно. В момент `expectedExpiryUtc` и позже таймер считается достаточным основанием: предварительный Internet-probe больше не нужен. Поэтому после сна/выключения, если машина запускается заметно позже границы (например, через 32 часа после последней успешной авторизации), первый подходящий tick сразу переходит к `stepOne`.

Первый успешный `stepTwo` должен быть получен явной командой `connect`: пока сохранённой 24-часовой точки нет, фоновый агент сам не начинает авторизацию. Явная команда `connect` обходит 24-часовой gate и действительно отправляет `stepOne`; если портал отвечает, что доступ ещё активен, таймер предыдущей успешной авторизации не изменяется.

Если `stepOne`, отправленный прямо у 24-часовой границы, сообщает, что прежняя авторизация ещё действует, это не сдвигает 24-часовой таймер и не запускает фиксированную паузу. До конца guard-window агент временно включает быстрый edge-watch и отправляет следующую разрешённую попытку сразу после подтверждённого фактического обрыва. После выхода за guard-window постоянные Internet-probe прекращаются.

## Автоматическая авторизация

Если фактический обрыв замечен внутри 10-секундного предграничного guard-window либо наступил/прошёл `expectedExpiryUtc`, агент по умолчанию подтверждает, что текущий SSID начинается с `Campus Wi-Fi`. Пользователь может явно включить настройку `IgnoreNetworkCheck`; в этом режиме проверка SSID/сетевого адаптера вообще не участвует в решении и агент пробует обычный captive flow по текущей маршрутизации. Это покрывает USB-раздачу, VPN/proxy/WARP, несколько сетей и другие конфигурации, которые Windows не может корректно свести к одному Wi-Fi SSID. После сетевой политики выполняется минимальный путь:

```text
baseline /pushmessages
→ POST /stepOne
→ GET /pushmessages по быстрому абсолютному расписанию
→ свежий 4-значный код только в памяти
→ direct POST /stepTwo
→ проверка Internet
```

`GET /stepTwo` и `GET /stepThree` отсутствуют. В журнал не записываются Bearer, SMS-код или Wi-Fi-код.

На один автоматический цикл разрешено максимум четыре фактических отправки `stepOne`. Каждая отправка получает полный быстрый polling schedule. Если свежий код за это окно не появился — в том числе при потерянном HTTP-ответе `stepOne` или штатном `302 → stepTwo` без кода — попытка считается потраченной и следующая `stepOne` разрешается после 15, 30 и 60 секунд. HTTP 429 и прочие явные terminal 4xx останавливают цикл раньше. HTTP 401 от `/mobile/pushmessages` помечается как `bearer-invalid` и требует повторной регистрации. После четвёртой отправки `stepOne` автоматические попытки блокируются до явной команды `connect`.

Если свежий Wi-Fi-код появился, он считается достаточным доказательством того, что backend обработал `stepOne`: клиент переходит прямо к `stepTwo`, не ожидая browser-facing `302`. Если кода нет по завершении полного polling schedule, автоматический цикл может перейти к следующей разрешённой `stepOne`. Если HTTP-ответ `stepTwo` потерян, код повторно не отправляется: клиент только проверяет появление Интернета по recovery schedule `0, 250, 500, 1000, 2000, 4000 ms`; успешный side effect принимается как успех.

## Ограничения первого MVP

- Production HTTP намеренно использует системный DNS. Cached-IP/direct-connect был полево проверен и оставлен только как эксперимент: stale-IP штраф оказался заметно хуже измеренного выигрыша.
- Ветка с непустым `addresses` намеренно не угадывает схему выбора `userId`.
- Проверка наличия Интернета использует локальный `http://online.susu.ru/` с отключёнными редиректами; Online подтверждается только ожидаемым `3xx` на `https://online.susu.ru/`.
