# Аудит сопровождаемости и план небольшого рефакторинга

Дата: 1 октября 2026 года. Статус: S0 выполнен; последующий архитектурный рефакторинг
остаётся предложением. Локально выполнены отдельные исправления F1/F2/F9 и фиксация Sheets перед dedupe.
Развёртывание сервера не выполнялось, актуальность исходного вложения относительно
deployment ещё требует подтверждения владельца.

Текущее расположение обязанностей: [короткая карта проекта](project-map.md).
Команды по зонам: [checks.md](checks.md). Целевая структура ниже ещё не реализована.

Цель: уменьшить объём кода, который нужно удерживать в голове для одного изменения; сделать UI удобным для проектирования и проверки; дать одному ИИ-агенту возможность выполнять обычные задачи без отдельного оркестратора.

## 1. Решение

Сохранить C#/.NET, текущий консольный renderer, два production-проекта App/Core и Google Apps Script с Sheets. Начать с границ UI, явного владения состоянием и воспроизводимых проверок. Остановиться после минимального пакета ниже, если добавлять и проверять экран стало удобно.

Само количество строк не является критерием успеха. Не нужны новый UI-фреймворк, DI-контейнер, mediator/event bus, универсальная система виджетов, новая база данных или новая схема серверного API. Специальная архитектура для нескольких параллельных агентов тоже не нужна: основной режим — один агент, одна законченная задача, один проверяемый diff.

Продукт используется бета-тестерами. Это позволяет менять внутреннюю структуру без поддержки стабильного программного API для сторонних разработчиков. Но настройки, регистрация, очередь телеметрии, серверные строки и поведение авторизации уже имеют пользователей; их совместимость сохраняется.

## 3. Основные результаты аудита

Приоритеты ниже относятся к сопровождаемости и порядку работ, а не к тяжести подтверждённых аварий.

### F1. Перед рефакторингом серверу нужна согласованная исходная версия — высокий приоритет

Серверный код намеренно отсутствует в публичном репозитории. Это зафиксировано в `docs/telemetry.md:115`. Офлайн-тест существует, но получает внешний файл через аргумент и не включён в найденные CI workflows.

У приложенного файла есть два воспроизводимых расхождения с репозиторным контрактом:

| Сценарий | Ожидание теста/документации | Приложенный скрипт |
|---|---|---|
| У одной установки несколько строк с разными никами, действий rename ещё нет | Последний исторический ник; в тесте «Алекс» | Первый ник; в тесте «WiFi King» |
| Исторические строки с отсутствующим/невалидным `install_id` | Сохранить как независимые позиции | Полностью исключить из публичного результата |

Доказательства: `tests/leaderboard_server_contract.cjs:132` и сценарий legacy-строк перед проверкой `total === 3` в строке 203; функции `loadLeaderboardLifecycleContext_` и `getPublicLeaderboard_` во вложении. Во втором независимом прогоне две legacy-строки дали `total: 0` вместо ожидаемых `2`.

Это подтверждённое рассогласование кода и контракта. Без истории актуального deployment нельзя честно объявить, что неверна именно работающая серверная версия. Для будущего этапа B0 разумный исходный вариант — сохранить существующий контракт теста и документации, если владелец не подтвердит намеренное изменение политики. Не маскировать расхождения ослаблением тестов в коммите переноса файлов.

Исправление к предыдущей оценке: `setupSheets` и серверные self-test entry points отсутствуют намеренно. Их отсутствие проверяет тест, а документация запрещает поставлять destructive setup в рабочий скрипт. Пустые заголовки этих секций — след форматирования, не отсутствующая функциональность.

### F2. Отрисовка прогресса находится на пути ручной авторизации — высокий приоритет

`AuthorizationFlow.cs:279` синхронно сообщает `FreshCodeReceived`, а `:296` — `StepTwoStarted`, до вызова отправки кода. `ReportProgress` в `:589` непосредственно вызывает callback. В `Program.cs:1645` callback обновляет историю, затем всегда вызывает `GetInteractiveStatusSnapshot()` и `ShowActionProgress()` (`:1683`). Даже ветка `StepTwoStarted`, не меняющая текст, доходит до общего рисования.

`GetInteractiveStatusSnapshot` в `Program.cs:2531` создаёт весь `ApplicationRuntime`: настройки, stores, сетевые клиенты и другие зависимости. Само создание не означает HTTP-запрос, но добавляет подготовку и локальные обращения перед сетевым шагом. Медленная консоль или чтение состояния могут задерживать ручной flow; размер задержки не измерялся.

Полезное изменение: callback только складывает небольшие сообщения прогресса в память; UI читает их и рисует в своём цикле. Ядро, расписание polling и порядок сетевых шагов сохраняются. Это отдельный поведенческий этап A2, а не скрытая часть механического переноса.

Локально исправлено 2026-10-01: `App/ManualAuthorizationRunner.cs` запускает flow
отдельно, callback только добавляет stage в concurrent queue. Один consumer
обновляет историю и рисует пакет накопленных стадий с исходным снимком статуса;
финальный статус собирается после завершения. C# тест проверяет заблокированный
renderer, порядок/доставку последних стадий, ошибки flow и ожидание завершения
авторизации при ошибке терминала. Core и сетевые алгоритмы не изменены.

### F3. Две части UI — один объект с множеством ролей — высокий приоритет

`InteractiveTerminalUi.cs` владеет клавиатурой, меню, общим состоянием, анимацией, layout, диалогами, кадром и выводом ANSI/ConsoleColor. `InteractiveTerminalUi.SpeedTools.cs` — partial того же класса: помимо рисования он запускает измерение, запрашивает backend, сохраняет ник и меняет участие в рейтинге.

Например, `RunSpeedToolsAsync:150`, `PublishLastSpeedResultAsync:410` и `SaveLeaderboardNicknameAsync:479` непосредственно вызывают сервисы и меняют состояние. `speed*`-поля при этом находятся в общем объекте UI. Новый экран легко начинает зависеть от чужого состояния.

Полезная граница уже есть: `Cell[,]`. Её можно использовать для независимого построения кадра. Недавний выбор адаптера и развёрнутый рейтинг также показывают реальное повторение полноразмерной компоновки; здесь оправдан один общий расчёт области списка.

### F4. Тесты хорошо защищают Core, слабее — пользовательские сценарии — высокий приоритет для переносов

`tests/IS74Wifi.ContractTests/IS74Wifi.ContractTests.csproj` ссылается только на Core. Есть содержательные сценарии раннего stepTwo, потерянного ответа, бюджета попыток, сетевого маршрута, телеметрии и политики агента.

Для UI и `Program.cs` много проверок написания исходника: фиксированные пути, `split` по объявлениям методов, поиск текстовых фрагментов (`static_checks.py:150`, `ui_live_status_contract.py:9`). Они полезны как напоминания об ограничениях, но не проверяют реальную навигацию, кадры или apply/rollback обновления. Перенос метода может ломать такой тест без изменения поведения; ошибка поведения может пройти при сохранении искомой строки.

Добавлять поведенческие проверки по мере выделения компонентов. Не требуется сначала покрыть весь продукт и не требуется менять тестовый framework. Проверки текста удалять только после появления эквивалентной проверки важного поведения либо сохранять как явно структурные правила.

### F5. `Program.cs` перегружен сценариями; есть реальное дублирование — средний приоритет

В одном файле находятся dispatch, bootstrap, установка, self-update/helper, регистрация, меню, статусы, настройки, диагностика и agent host. При этом важные сервисы уже существуют: `ApplicationRuntime`, `UpdateMaintenanceService`, `ProgramInstallation`, `GitHubUpdateClient`, `AgentService`.

`RegisterAsync:233` и `RegisterFromMenuAsync:1975` повторяют цепочку confirmation → token → запись secrets/session → device metadata → telemetry. Политики изменения настроек и перезапуска агента тоже находятся рядом с показом сообщений (`SetDirectNetworkAdapter:2957`, `SetIgnoreNetworkCheck:2976`).

Переносить целые сценарии в несколько владельцев, используя существующие сервисы. Длинный понятный `switch` маршрутизации допустим. Простое создание `Program.Update.cs` уменьшит размер страницы, но оставит прежнюю связанность; это допустимый временный приём, не критерий завершения.

### F6. Чтение состояния и сборка зависимостей имеют неочевидные эффекты — средний приоритет

Периодическое `ReadLocalInteractiveStatusSnapshot` уже специально не создаёт network runtime. Другие status-вызовы его создают. `SettingsStore.Load()` может создать файл настроек, а `UpdateMaintenanceService.LoadState()` — нормализовать и сохранить update state. Поэтому выражение «только читаем состояние» сейчас не всегда означает отсутствие записи.

Нужен один владелец сбора статуса и явно описанное место начальной подготовки/нормализации. Сначала сохранить фактическое поведение и записать его тестом. Разделение на read и normalize делать отдельным изменением, если оно действительно нужно. Не вводить универсальный repository layer и не объявлять потерю настроек доказанным багом без воспроизведения.

### F7. Сервер уже имеет логические разделы, но чтение Sheets смешано с правилами — средний приоритет

Валидация вынесена в функции, используются allowlist полей, типизированные ограничения, пакетная запись и lock. Это полезные существующие границы.

`loadLeaderboardLifecycleContext_` одновременно читает оба листа и восстанавливает состояние участников. `getPublicLeaderboard_` читает данные, выбирает результат, сортирует, скрывает внутренние поля и формирует HTTP-ответ. `handleLeaderboardControl_` совмещает проверку команды, правила cooldown, lock и запись.

Сначала разнести текущие функции по нескольким файлам. Затем при очередной правке рейтинга отделить чистые функции `rows → state` и `state + command + now → decision`. Схемы могут оставаться длинными массивами: превращать их в собственный язык описания типов не требуется.

### F8. Документация могла увести следующего агента в неверную сторону — исправлено в S0

При исходном аудите `docs/speed-tools-ui.md` указывал пункт `[9]` вместо `[2]` и
отложенную публикацию рейтинга, которую `CampusSpeedToolsService.PublishAsync`

В S0 исправлены меню, согласие/очередь рейтинга и описание DNS; исторические документы

### F9. Отложенный speed_test блокировал общий telemetry batch — исправлено локально

Дополнительная проверка после первого отчёта выявила несовместимость:
`CampusSpeedToolsService` ставит неудавшийся замер в общую очередь,
`TelemetryClient.SendTelemetryBatchAsync` отправляет её через `route=telemetry`,
а исходный сервер отвергал `speed_test` на этом маршруте. Загрузчик сохраняет
отклонённый пакет и повторяет его после backoff, задерживая дальнейшую отправку.

В приватном `IntersvyazAutomaticWifi_SERVER/Code.gs` этот маршрут теперь принимает
замеры отдельно и в смешанном пакете. Запрет отложенных публикаций рейтинга
сохранён. Новый `tests/server_ingestion_contract.cjs` воспроизводит отказ исходного
вложения и проходит на исправленном сервере. Общий синтетический JSON проверяется
также C# serializer/uploader: отказ не удаляет очередь, backoff соблюдается,
после совместимого ответа очередь очищается без смены payload/batch identity.

Там же исправлены оба расхождения F1 без изменения существующих ожиданий теста:
последний исторический ник, приоритет lifecycle-действий, независимые legacy-строки.
Добавлен flush под lock до dedupe-маркеров и до чтения записанного lifecycle action.
Серверный исходник в публичный репозиторий не переносился. Приватный README содержит
SHA-256 исходного вложения, команду `verify.ps1` и порядок ручного rollout.

На исправленном checkout прошли: 20 групп C# contract suite, 14 сценариев рейтинга,
8 групп ingestion-сценариев, обе Python-проверки, PowerShell critical-path и сборка
App в `artifacts/audit-fixes` (те же 9 nullable-предупреждений). Реальный сервер,
ручная авторизация и визуальная сессия приложения не использовались как тест.

Последующее согласованное изменение: добавлены умеренные минутные лимиты по
`install_id` (12 telemetry batches, по 6 speedtest/leaderboard, 30 control),
общий 15-секундный кеш публичного рейтинга с invalidation и единый ответ
`rate_limited` / `retry_after_seconds`. Клиент сохраняет данные при ограничении
и соблюдает задержку. Общие JSON-примеры проверяют все восемь типов событий с
обеих сторон. Точные правила и порядок обновления описаны в `docs/telemetry.md`.
Это best-effort ограничения CacheService, не строгие квоты: раннее вытеснение
счётчиков возможно. Новые ID остаются обходом по явному решению владельца;
аккаунты, приглашения, глобальные бюджеты и выключатель записи не добавлены.

## 4. Отдельные серверные вопросы; не смешивать с переносом файлов

1. Полное чтение истории `Leaderboard` и `LeaderboardActions` выполняется для рейтинга и status/control, иногда повторно после изменения; status также берёт общий write-lock. Стоимость растёт с числом строк. Для небольшого бета-теста это не доказанная проблема задержек. Сначала измерить количество прочитанных строк/длительность, затем решать о сокращении чтений.
2. `appendEvents_` записывает группы в разные листы последовательно, а dedupe-cache обновляет после всех записей. Ошибка на втором листе оставляет уже записанную первую группу; повтор может создать дубликаты. Это вывод из порядка операций, не воспроизведённая авария Sheets. Минимальная проверка — смоделировать ошибку второй записи и зафиксировать семантику повторов. Lock не следует называть транзакцией нескольких листов.
3. Дедупликация через cache уже описана в исходнике как временная; не обещать exactly-once. Google допускает удаление данных cache раньше заданного срока: [Cache reference](https://developers.google.com/apps-script/reference/cache/cache#put(String,String,Integer)).
4. В исходном вложении в двух write-paths lock освобождался без явного `SpreadsheetApp.flush()`. Google рекомендует flush перед release при работе с таблицей: [Lock reference](https://developers.google.com/apps-script/reference/lock/lock#releaseLock()). Локально исправлено и проверено fake buffered Sheets (см. F9); фактическая потеря данных в production не установлена. Это не превращает несколько листов в транзакцию.
5. Анонимный endpoint и client-generated `install_id` сохраняются по решению владельца. Умеренные минутные ограничения и кеш уже добавлены (см. F9 и `docs/telemetry.md`), но ID не доказывает личность участника и смена ID обходит персональные лимиты. Усиление идентификации не входит в согласованный объём работ.

## 5. Целевая карта ответственности приложения

Это места назначения при соответствующем этапе, не требование немедленно создать все файлы. Небольшие record/enum остаются рядом с владельцем; namespace и проекты массово не переименовываются.

| Файл/группа в App | Ответственность | Что туда не переносить |
|---|---|---|
| `Program.cs` | STA entry point, выбор режима, внешняя обработка ошибок | Порядок регистрации, рисование, копирование EXE |
| `ApplicationRuntime.cs` — существующий | Создание и lifetime сетевых/основных сервисов | UI-координаты, бизнес-решения отдельных экранов |
| `StatusService.cs` | Локальный снимок, отдельное сетевое обновление, данные подробного отчёта | Управление вводом и прямое рисование |
| `InteractiveMenuController.cs` | Выполнение выбранных действий, onboarding, показ результата через UI | HTTP-реализация, низкоуровневая замена EXE |
| `RegistrationWorkflow.cs` | Одна цепочка регистрации для CLI и меню | Console.ReadLine и координаты терминала |
| `SettingsActions.cs` | Сохранение пользовательских настроек и существующие правила перезапуска агента | Реализация JSON/Windows API |

В первом пакете `MainMenuScreen`, `Dialogs`, `RegistrationWorkflow`, `SettingsActions` можно не выделять. Польза сначала достигается на одном списке, общих примитивах и ручной авторизации.

Позже, только при работе над этими функциями:

| Файл | Откуда переносить |
|---|---|
| `AppBootstrap.cs` | `BootstrapInteractiveLaunch`, `TryForwardToInstalledCopy`, local-run policy |
| `InstallationActions.cs` | Установка, включение/выключение автозапуска, reset/uninstall; использовать существующий `ProgramInstallation` |
| `UpdateWorkflow.cs` | Проверка/скачивание/подготовка, интеграция с существующим `UpdateMaintenanceService`, интерактивный и автоматический запуск |
| `UpdateApplyHelper.cs` | Проверка аргументов helper, ожидание parent, staging, replacement, rollback, restart, cleanup |
| `AgentHost.cs` | Цикл `RunAgentAsync`, stop/wake/resume и вызовы maintenance; политика остаётся в `AgentService` |
| `DiagnosticsCommands.cs` | Сетевые диагностические сценарии и CLI-форматирование |

Core в этом плане сохраняет существующие классы. Папки по темам можно добавить при реальной работе с подсистемой; массовый перенос десятков небольших файлов только для симметрии не нужен. `AuthorizationFlow`, `PushPollingEngine`, `DirectNetworkConnector`, `Is74SpeedTestProvider` и JSON wire-модели не перерабатываются ради размера.

### Правила границ

- Экран получает конкретную модель, размер окна и при необходимости время/фазу анимации; строит `Cell[,]`. Не вводить универсальную модель всех возможных экранов.
- Управление клавишами меняет локальное состояние экрана или возвращает действие. Сетевые запросы и сохранение выполняет контроллер/сценарий.
- `TerminalOutput` хранит предыдущий кадр всей сессии: переход между экранами не должен создавать новый framebuffer и мерцание.
- В одной интерактивной сессии остаётся один ожидающий `ReadKey`. Нельзя заводить нового потребителя клавиатуры при каждом кадре или запускать второй после отмены первого без разбора его lifetime.
- UI-состояние скорости принадлежит только экрану/контроллеру скорости; общий `ApplicationRuntime` не передаётся в renderer.
- Предпочтительны обычные классы и небольшие callbacks. Интерфейс вводится для конкретной внешней границы или второй реализации: например, CLI/UI ввод регистрации либо тестовая подмена ввода. Не нужен `I...` для каждого класса.
- Компактный и полноэкранный режимы используют одни действия и правила, различается представление. Их объединение не должно менять отмену и горячие клавиши.

## 6. Целевая карта backend

Серверный исходник хранится в отдельном приватном Git-каталоге/репозитории, доступном выполняющему задачу агенту. Не копировать его автоматически в публичный репозиторий приложения. Публичный репозиторий может содержать описание контракта, безопасные fixtures и тесты.

| Файл приватного backend | Содержимое |
|---|---|
| `Config.gs` | CONFIG; без автоматического доступа к Sheets при загрузке файла |
| `Schemas.gs` | Заголовки, allowlist полей, enum-значения в текущем порядке |
| `Api.gs` | `doGet`, `doPost`, route/envelope и JSON-ответ; вызов сценариев |
| `Validation.gs` | `validatePayload_`, validators типов событий, маленькие helpers |
| `Leaderboard.gs` | Сортировка, восстановление участия, команды, nickname policy |
| `SheetsStore.gs` | Чтение и проверка листов, `buildRow_`, append, lock/cache |

Шесть файлов — начальный вариант. Отдельный `ValidationHelpers.gs` нужен лишь если validators неудобно просматривать. Не делать файл на каждый enum или поле. `Schemas.gs` вполне может остаться самым длинным.

В Apps Script файлы выполняются в общей области видимости, а ES-module `import/export` не поддерживается. Физическое разделение само по себе не создаёт изоляцию. Сохранять уникальные имена, не добавлять верхнеуровневых действий с Sheets и учитывать порядок инициализации `const`; это описано в [документации V8](https://developers.google.com/apps-script/guides/v8-runtime#module_limitations).

При сохранении ручного деплоя разумен короткий скрипт сборки, который соединяет эти файлы в фиксированном порядке в `dist/Code.gs`. Это производный артефакт: его не редактируют. Офлайн-тесты прогоняются против того же собранного файла, который переносится в Apps Script; фиксируются его hash и соответствующая версия deployment. Такой вариант позволяет продолжать вставлять один файл и не заводить новый сервис деплоя. Собранный файл не должен одновременно деплоиться вместе со своими исходными частями.

Контракт schema 4, строки ошибок, route, порядок столбцов и текущий `/exec` сохраняются при структурном переносе. Разбиение validators и registry событий нельзя одновременно использовать для изменения схемы или правил данных.

## 7. Небольшие самостоятельные этапы

У каждого этапа один владелец-агент. Он читает этот документ, выполняет только карточку и её проверки, обновляет статус и передаёт результат. Технически возможная параллельность здесь не является целью. «Зависит от» означает, что исходный checkout уже содержит завершённый предыдущий этап.

### S0 — сделать карту и проверки пригодными для следующего агента

- Зависит от: ничего. Риск низкий.
- Файлы: короткий корневой `AGENTS.md`, этот план, README/релевантные docs, `scripts/check.ps1`, CI.
- Сделать: карту владельцев поведения; исправить F8; явно отличить PowerShell/reference и неиспользуемый cached-IP эксперимент от текущего C# пути; записать команды проверки. Wrapper должен возвращать ненулевой exit code при первом сбое, а не скрывать его последней удачной командой.

## 9. Как работать без постоянного оркестратора

Один короткий `AGENTS.md` и этот план достаточны. В AGENTS — только повседневная навигация и ограничения, около одной-двух страниц, не копия всех документов.

Предлагаемое содержимое AGENTS:

1. Где менять экран, сценарий, Core-алгоритм и wire-contract; ссылки на владельцев из карты.
2. Какие команды проверки запускать по зонам и где брать приватный backend; отсутствие доступа указывать явно.
3. Границы: renderer без I/O; один keyboard reader; progress не блокирует flow; алгоритмы авторизации/лимиты/schema меняются только в явно посвящённой им задаче.
4. Локальная проверка UI использует `IS74W_RUN_LOCAL=1`, но эта переменная только отключает forwarding/install bootstrap: она не изолирует settings и регистрацию. Для автоматических проверок нужны временные stores и fake внешние службы.
5. Не переносить приватный server source в публичный Git. Не редактировать сгенерированный bundle. Не возвращать setup/migration entry points.
6. В одной задаче одна ответственность; не добавлять framework, новую подсистему или соседние исправления ради завершения маленькой правки. Сохранять чужие изменения.
7. В результате указывать: что изменено, какие проверки выполнены, что не проверялось, нужна ли совместная смена версии клиента/сервера.

## 10. Проверки и ограничения по объёму

Существующие команды из корня приложения:

```powershell
dotnet build .\IS74Wifi.slnx -c Debug --no-restore
dotnet run --project .\tests\IS74Wifi.ContractTests\IS74Wifi.ContractTests.csproj -c Debug --no-build
python .\tests\static_checks.py
python .\tests\ui_live_status_contract.py
.\tests\critical_path_contract.ps1
node .\tests\leaderboard_server_contract.cjs <private-server-file>
git diff --check
```

На чистом checkout сначала нужен restore. Полный Windows suite использует DPAPI/WLAN и тестовые записи реестра; ограниченная среда может требовать дополнительных прав. Заблокированный запущенным приложением EXE — проблема выходного файла, не ошибка C#; сборку проверки можно направить в отдельный `artifacts`-каталог. Backend-тест красный на исходном вложении по F1; на исправленном приватном `Code.gs` оба серверных suite проходят (см. F9).

В S0 wrapper должен различать проверки: App/UI; Core; private backend; полную pre-release. Не запускать Wi-Fi авторизацию, реальный speedtest, install/uninstall или HTTP POST в production в составе «обычной проверки».

Ориентир размера функции/файла — удобство чтения одной ответственности. Файл с 600 строками схем допустим, файл на 180 строк, который и сохраняет настройки, и управляет сетью, и рисует, заслуживает внимания. Не ставить обязательный порог строк или процент покрытия.

Рефакторинг окупился, если:

- обычная визуальная правка не затрагивает backend и сценарии App;
- для нового экрана есть один рабочий пример и проверка без терминала;
- правила участия/регистрации имеют одного владельца;
- проверяемый серверный артефакт совпадает с подготовленным к deployment;
- новый агент находит нужную зону по карте, а не восстанавливает решения по чатам;
- после каждого этапа продукт собирается, а тестовые ограничения явно известны.
