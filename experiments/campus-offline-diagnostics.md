# Автономное исследование Campus / VPN

`campus-offline-diagnostics.cmd` запускает интерактивный Python 3 скрипт без
сторонних пакетов. Windows, установленный Python и Windows PowerShell 5.1 обязательны.
Это отдельный полевой эксперимент, не routine check и не реализация C# runtime.
Запуск из репозитория: `python experiments/campus-offline-diagnostics.py --output artifacts/campus-offline`.
Для автономного запуска скопируйте `.py` и оба `.cmd` в отдельную папку вне checkout.

Сначала с работающим Интернетом получаются IPv4 трёх известных серверов через
системный DNS (срок ожидания одного имени до 15 секунд). Источник может быть LTE/VPN;
это кандидаты, не подтверждённые адреса Campus. При отсутствии DNS разрешён ручной
ввод IPv4. Список не обновляется автоматически после сетевых отказов.

Пользователь выбирает физический Wi-Fi, вручную подтверждает Campus и переключает
состояния. При выборе вводится порядковый номер адаптера из списка, не телефон;
некорректный ввод предлагает повторить выбор и не сохраняется в журнал.
Далее проверяются
состояния: captive/VPN OFF, captive/VPN ON, затем опционально ручная авторизация
и Internet/VPN OFF/ON. Можно пропустить этап, завершить опыт через q или Ctrl+C.
Отдельно требуется приостановить автоавторизацию IS74Wifi. Скрипт не управляет
адаптерами, службами, VPN, Radmin или настройками Windows. Обычный режим не запускает авторизацию.
При отключении LTE/Radmin удалённое управление ожидаемо теряется; процесс работает локально.
Для второго этапа VPN устанавливается заранее на LTE; затем LTE отключается при
оставленном включённым VPN-клиенте. Состояние connected/reconnecting после потери LTE
записывает пользователь; скрипт не доказывает активность туннеля. SSID подтверждает
оператор; скрипт его не определяет. Это моделирование потери underlay через смену
LTE → Wi-Fi, не точное воспроизведение истечения авторизации на неизменном Wi-Fi.

На этап: 10 пар новых TCP/HTTP соединений к `http://online.susu.ru/` по одному
сохранённому IP (без DNS), затем 3 пары со свежим UDP A-запросом через DNS выбранного
Wi-Fi. Первая проба имеет общий бюджет 2 секунды, вторая — 300 мс, пауза — 500 мс.
`--pairs 1` сокращает эксперимент. DNS использует до 900 мс на сервер, ограниченные
общим бюджетом; системного fallback в этой сравнительной ветке нет. Это сравнение
Python-механизмов, не точная копия DNS-политики/HTTP stack C#.

Затем выполняются GET `/` к `http://w.is74.ru/` и `https://api.is74.ru/` по максимум
трём сохранённым адресам на сервер (до 3 секунд на адрес). Все сокеты имеют
`IP_UNICAST_IF` в network byte order и bind исходного IPv4. TLS проверяет сертификат
и исходное имя API через `ssl.create_default_context`, HTTP сохраняет Host.
В Python-пробах редиректы не выполняются, тела/куки/полные Location не сохраняются, stepOne/stepTwo,
pushmessages, SMS и Bearer не используются. HTTP 200 — лишь кандидат captive,
не доказательство оператора или актуальности IP. Привязка сокета не заменяет capture.

Смена индекса/IPv4/DNS выбранного адаптера между началом и концом этапа отмечается
как неустойчивый binding; краткие изменения посередине и смена SSID этим не исключаются.
Для каждого этапа сохраняются заявленные условия и снимок адаптеров. `results.jsonl`
сбрасывается на диск после каждой записи и остаётся при прерывании. Данные содержат
локальные адреса/идентификаторы и предназначены для приватного разбора. Для записи
в checkout всегда указывайте игнорируемый каталог `artifacts/`, результаты не коммитить.

Проверка без сети: компиляция Python, `--help` и синтетические DNS/HTTP fixtures.
Полевой запуск выполняет только владелец по явной инструкции. Полный C# check suite
не проверяет этот инструмент; приложение, wire schema и backend не меняются.

## Отдельный сценарий с реальной авторизацией

`campus-vpn-auth.cmd` (или Python с `--vpn-auth`) запускает отдельный мастер:
получить IP на LTE → подтвердить установленный VPN → убрать LTE/другие интернет-пути,
сохранив VPN-клиент → подтвердить неавторизованный прямой Campus → две bound IP-пробы
→ проверить неизменность binding → явно разрешить одну команду `IS74Wifi.exe connect`
словом `АВТОРИЗОВАТЬ` → три IP-пробы после попытки. Автоповтора команды нет.

Используется установленный `%LOCALAPPDATA%/Programs/IS74Wifi/IS74Wifi.exe` либо `--app`.
Регистрация должна быть выполнена заранее в самом приложении. Проверяется лишь
наличие `secrets.dpapi`; содержимое секретов не читается. Скрипт не регистрирует
устройство, не спрашивает телефон/код и не реализует второй протокол авторизации.
Его Python-пробы не подменяют защитные проверки клиента и не подтверждают оператора.
Установленный клиент сам выбирает путь; пользователь должен убрать остальные
интернет-подключения. Это проверка текущего C# runtime с его DNS-политикой,
**не проверка новой IP-only авторизации**. Connect использует штатные локальные
состояния, лимиты и настройки клиента, включая существующее согласие на статистику.

На диск записываются SHA-256 EXE, начало/окончание команды, exit code, длительность,
путь и размеры diagnostic.log до/после, снимки интерфейсов и результаты проб.
Вывод клиента виден в окне; секреты и сырой diagnostic.log в отчёт не копируются.
Exit code 0 включает AlreadyOnline/AlreadyAuthorized и не доказывает новый stepTwo.
Детальный исход следует сверять с отдельным diagnostic.log и post-probes.
Команда не имеет принудительного тайм-аута: завершение CLI не гарантирует отмену
agent-owned операции. Ctrl+C сохраняет уже записанное; перед новой попыткой нужно
убедиться, что предыдущая операция клиента закончилась.
