# Прямое подключение через физический адаптер (экспериментальная C#-функция)

При включённом VPN IS74Wifi может авторизовать **саму физическую сеть**, не отключая VPN для остальных программ. Это не изменение глобальной таблицы маршрутов, firewall или kill switch.

## Режимы

- **Автоматически** (по умолчанию): выбрать работающий `Campus Wi-Fi*`, иначе активный физический Wi-Fi, затем физический Ethernet/USB-RNDIS. VPN/TAP/TUN и очевидные виртуальные адаптеры не выбираются автоматически. Подозрительные Ethernet-интерфейсы видны в ручном списке с предупреждением: пользователь может исправить ошибочную классификацию.
- **Выбрать вручную**: `Настройки → Адаптер для авторизации`. Выбор хранится по постоянному Windows ID интерфейса. Если он отключён или удалён, запросы **не перенаправляются** на другой адаптер/VPN.
- **Системный маршрут**: явный вариант для несовместимых конфигураций; возвращает прежнее поведение Windows и может идти через VPN. Это не автоматический fallback.

Выбор конкретного адаптера **не меняет** существующую настройку `[3] Проверка сети`: при включении авторизация по-прежнему разрешена только на `Campus Wi-Fi*`, при отключении SSID gate не применяется (например, USB-раздача или Ethernet).

## Механизм

В `ApplicationRuntime` три строго выделенных клиента — API, portal и `online.susu.ru` — используют один `DirectNetworkConnector`. Каждый новый сокет TCP/UDP получает физический IPv4 исходного интерфейса и Windows `IP_UNICAST_IF`; `UseProxy=false`. DNS A-запросы отправляются по UDP/53 DNS-серверам, назначенным **этому же интерфейсу**, а не через системный/VPN resolver; успешные ответы кэшируются на 30 секунд с ключом adapter ID + IPv4 + SSID + DNS. Перенаправления на посторонние домены не разрешены. HTTPS сохраняет исходное имя запроса для TLS/SNI и проверки сертификата.

Долгоживущие HTTP-соединения обновляются не реже раза в 10 секунд; новые сокеты заново выбирают доступный адаптер. После смены сетевого подключения/wake Windows существующий агент пробуждается по уведомлению ОС и пересчитывает состояние, а привязки новых сокетов берутся из текущих параметров адаптера. Ручное изменение настройки перезапускает фоновый агент.

Перед резервированием одной из четырёх автоматических попыток `stepOne` клиент делает отдельное TCP-подключение к `w.is74.ru:443` через выбранный адаптер. Эта проверка ничего не отправляет в captive portal. Если она не проходит, происходит обычный pre-step retry без расходования попытки. Базовый API baseline также идёт напрямую и при ошибке не расходует бюджет. Если VPN/WFP блокирует прямое подключение **после** предварительной проверки, возможна обычная транспортная ошибка — абсолютной гарантии исключения гонки нет.

DNS и сокеты сейчас работают только с IPv4. DNS-серверы, доступные только через IPv6/DoH или скрытый VPN-локальный прокси, потребуют другой реализации. Нет резервного системного DNS или перехода на VPN, если прямой путь недоступен. Это намеренно, чтобы не выдавать запросы через неправильный маршрут.

## Диагностика и ограничения

`IS74Wifi.exe network-diagnose` либо `Настройки → Проверить прямое подключение` выполняет только:

1. Определение физического адаптера и наличия IPv4/DNS.
2. DNS через выбранный интерфейс и TCP к `w.is74.ru:443`.
3. GET главной страницы портала для проверки TLS, без отправки формы.
4. GET `api.is74.ru/mobile/pushmessages?page=1&pageSize=1` **без Bearer**: HTTP 401 означает, что сервер достижим (другой HTTP-ответ тоже подтверждает TLS, но требует отдельной интерпретации).
5. HTTP GET `online.susu.ru` **только заголовки**, без следования редиректам, с прямым маршрутом.

Диагностика не запускает телефонную регистрацию и не расходует попытки `stepOne`. При включённом kill switch VPN может блокировать физические пакеты системными правилами; в таком случае программа показывает сетевую ошибку. Привязка IP/interface не способна отменить блокирующие политики VPN и сама по себе не доказывает, через какой физический канал пакет реально вышел; это проверяется трассировкой пакетов на Windows.

Остальной трафик (`telemetry`, `updates`, `speedtest`, браузер) использует прежние независимые HTTP-клиенты/системную маршрутизацию. Никакие новые сетевые идентификаторы или DNS/IP не добавлены в удалённую телеметрию.

**Полевой тест на Windows необходим:** проверить прямой и системный режим с выключенным VPN, затем с включённым VPN (включая kill switch), переход между двумя Wi-Fi, wake/resume и обновление из обычной установки. В Linux CI доступны только статические/чистые контрактные тесты; они не подтверждают фактическую маршрутизацию WinSock или правила WFP.
