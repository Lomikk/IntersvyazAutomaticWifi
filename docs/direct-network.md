# Прямое подключение через физический адаптер (экспериментальная C#-функция)

При включённом VPN IS74Wifi может авторизовать **саму физическую сеть**, не отключая VPN для остальных программ. Это не изменение глобальной таблицы маршрутов, firewall или kill switch.

## Текущая модель

Автоматический режим больше не выбирает один «лучший» адаптер. Программа перечисляет
все подтверждённые Windows hardware-интерфейсы с пригодным IPv4 (Wi-Fi, Ethernet,
USB/RNDIS), исключает VPN/виртуальные адаптеры и обслуживает каждый physical path
независимо. Для каждого path хранятся собственные probe/status/expiry/retry state.

`Campus Wi-Fi*` больше не является обязательным runtime gate: SSID используется только
как диагностический сигнал прямого подключения. Реальное решение принимает bound probe
конкретного path: normal `302 -> https://online.susu.ru/` означает Internet, HTTP 200 —
captive, transport/DNS failure не считается доказательством captive.

Обычный пользователь не выбирает адаптер и не отключает VPN. Старые поля
`IgnoreNetworkCheck` и `DirectNetworkAdapterId` пока читаются ради обратной совместимости
с установленными версиями, но path-aware agent/manual flow на них не опираются.

При нескольких captive-path одновременно запускается только один SMS-flow. Приоритет
получает physical path, который Windows сообщает как текущий Internet connection profile;
остальные обслуживаются последовательно.

## Механизм

В `ApplicationRuntime` три строго выделенных клиента — API, portal и `online.susu.ru` — используют один `DirectNetworkConnector`. Каждый новый **TCP**-сокет получает физический IPv4 исходного интерфейса и Windows `IP_UNICAST_IF`; `UseProxy=false`. Сначала DNS A-запросы отправляются через этот же интерфейс по UDP/53 его DNS-серверам. Если прямой DNS не отвечает, разрешён **только резервный поиск адреса** через системный DNS Windows; даже в этом случае HTTP/TLS-сокет остаётся привязанным к исходному интерфейсу, без автоматического перехода через VPN. В диагностике виден источник адреса. Прямые DNS-ответы кэшируются на 30 секунд, резервные — на 10 секунд; ключ учитывает adapter ID, IPv4, SSID и DNS. Перенаправления на посторонние домены не разрешены. HTTPS сохраняет исходное имя запроса для TLS/SNI и стандартной проверки сертификата.

Долгоживущие HTTP-соединения обновляются не реже раза в 10 секунд; новые сокеты заново выбирают доступный адаптер. После смены сетевого подключения/wake Windows существующий агент пробуждается по уведомлению ОС и пересчитывает состояние, а привязки новых сокетов берутся из текущих параметров адаптера. Ручное изменение настройки перезапускает фоновый агент.

Перед резервированием одной из четырёх автоматических попыток `stepOne` клиент делает отдельное TCP-подключение к **`w.is74.ru:80`**, действительному HTTP-порту captive portal, через выбранный адаптер. Эта проверка ничего не отправляет в captive portal. Если она не проходит, происходит обычный pre-step retry без расходования попытки. Базовый API baseline также идёт напрямую; при отказе DNS/маршрута он не расходует бюджет. Для прямого режима baseline получает максимальный тайм-аут 5 секунд вместо обычных 3, чтобы кратковременный отказ UDP DNS не прервал разрешение адреса. Если VPN/WFP блокирует прямое подключение **после** предварительной проверки, возможна обычная транспортная ошибка — абсолютной гарантии исключения гонки нет.

Прямой DNS и TCP работают только с IPv4. IPv6-адреса, возвращённые системным DNS, отбрасываются. Если системный DNS не работает либо VPN/WFP запрещает TCP вне VPN, приложение выдаёт ошибку: **fallback по HTTP/TCP не существует**. Системный DNS может использовать VPN **только для получения IP**; этот факт отображается в `network-diagnose`, и сам по себе не доказывает физический маршрут последующего TCP. Программа не изменяет правила VPN/WFP и не отключает kill switch.

## Диагностика и ограничения

`IS74Wifi.exe network-diagnose` либо `Настройки → Сеть и диагностика` выполняет live
bound-probe **каждого** активного physical path и показывает:

1. friendly name/SSID (если локальный Wi-Fi), IPv4, gateway и ifIndex;
2. какой path Windows считает preferred Internet underlay;
3. фактический статус `Internet / требуется авторизация / недоступен / неясно`;
4. сохранённую per-path ожидаемую границу и последнюю успешную авторизацию.

Диагностика не вызывает `stepOne`/`stepTwo`, не отправляет SMS и не меняет default route.
VPN/виртуальные интерфейсы в список authorization path не включаются. При включённом kill
switch VPN может блокировать physical packets системными правилами; в таком случае path
показывается как недоступный. При включённом kill switch VPN может блокировать физические пакеты системными правилами; в таком случае программа показывает сетевую ошибку. Привязка IP/interface не способна отменить блокирующие политики VPN и сама по себе не доказывает, через какой физический канал пакет реально вышел; это проверяется трассировкой пакетов на Windows.

Остальной трафик (`telemetry`, `updates`, `speedtest`, браузер) использует прежние независимые HTTP-клиенты/системную маршрутизацию. Никакие новые сетевые идентификаторы или DNS/IP не добавлены в удалённую телеметрию.

**Полевой тест на Windows необходим:** проверить прямой и системный режим с выключенным VPN, затем с включённым VPN (включая kill switch), переход между двумя Wi-Fi, wake/resume и обновление из обычной установки. В Linux CI доступны только статические/чистые контрактные тесты; они не подтверждают фактическую маршрутизацию WinSock или правила WFP.

### Windows 11: безопасный smoke-test перед выпуском

В PowerShell из корня репозитория (`D:\Repos\IntersvyazAutomaticWifi`), на ветке исправления:

```powershell
dotnet restore .\IS74Wifi.slnx
dotnet build .\IS74Wifi.slnx -c Release --no-restore
dotnet run --project .\tests\IS74Wifi.ContractTests\IS74Wifi.ContractTests.csproj -c Release --no-build
dotnet .\src\IS74Wifi.App\bin\Release\net10.0-windows10.0.19041.0\IS74Wifi.dll network-diagnose
```

Сначала проведите `network-diagnose` при выключенном VPN, затем с включённым (и, если применяется, с kill switch). Диагностика **не расходует попытки авторизации**, не запрашивает Bearer, не отключает VPN. В нормальном случае API вернёт `HTTP: 401`, портал — `TCP: доступен` на порту 80 и HTTP-ответ (обычно редирект). `DnsUnavailable` — не равно отказу TCP: в отчёте отдельно виден DNS fallback. Если VPN блокирует прямой маршрут, `TCP: недоступен` является ожидаемым результатом. Проверьте физический маршрут через системную трассировку/захват пакетов отдельно: успешный `curl --interface` или наш тест TCP сами по себе этого не доказывают.

Перед публикацией любых логов скройте личное имя/SSID адаптера, IPv4, DNS и сетевые идентификаторы. На сам сервер телеметрии эти сведения не добавляются.
