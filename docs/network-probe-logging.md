# Как объяснить проверки сети по журналу

В campus-test.8 причины проб и пробуждений добавлены в локальный `logs/diagnostic.log`.
Интервалы, число повторов, IP-first, авторизация, telemetry wire и состояние путей
не изменены. Новый периодический опрос и повтор после одиночной ошибки не добавлены.

В CLI `Unreachable` подписан «сбой проверки», ожидание события — «по событию».
Это не утверждение об отсутствии всего Интернета. TXT поясняет, что HTTP-ответ
не получен, а при event-driven режиме периодическая проверка не назначена.
Столбцы CLI учитывают длину новых подписей в окнах от 80 столбцов.

## Источники пробуждения

- `agent.worker start ... version=...`: версия фактически работающего worker,
  PID присутствует в каждой строке. Запущенное меню и установленный worker могут
  принадлежать разным сборкам; по версии/PID видно, откуда получены сведения.
- `agent.event source=WindowsAddress`: Windows вызвала `NetworkAddressChanged`.
- `agent.availability available=...` и `source=WindowsAvailability`: изменение
  доступности сети по Windows.
- `agent.ncsi connectivity-changed ... profiles-changed=...`: изменение принятого
  NCSI/profile snapshot; неизменившиеся NCSI callbacks по-прежнему отбрасываются.
- `source=Resume`: возобновление работы. `StartupOffline` в причине пробы —
  начальная синхронизация, когда NCSI при запуске уже не подтверждает Интернет.
- `source=ipc-complete (deadline-recompute-only)`: операция IPC завершена,
  scheduler проснулся пересчитать deadline. Сам по себе этот сигнал не требует
  второй HTTP-пробы и не устанавливает флаг изменения сети.
- `agent.wait authorization-ms=... effective-ms=...`: рассчитанное ожидание
  авторизационной сети и фактическое ожидание после учёта фоновой работы/resume fallback.
- `agent.wake source=signal|timeout|stop`: завершение WaitAny. При `signal` смотреть
  предшествующий event/IPC; при `timeout` — величины ожидания. Сигнал может прийти
  от другого процесса через named event. Пробуждение не равно сетевому запросу.

События Windows относятся к компьютеру в целом: callback изменения адресов сам
не сообщает, какой адаптер изменился. Событие на виртуальном/USB-интерфейсе тоже
может разбудить проверку выбранного Wi-Fi. Нельзя называть это переподключением
Wi-Fi без соответствующих данных WLAN журнала Windows.

## Причины реальных проверок

Каждая проверка `NetworkPathProbe` (координатор и IPC diagnostics) получает
`network.probe start id=N ...` и `result id=N ...`, либо `aborted id=N ...`.
Идентификатор уникален внутри процесса; сопоставлять вместе с PID.

| reason | Что произошло |
|---|---|
| `binding.appeared` / `binding.reappeared` / `binding.changed` | Новый/возвращённый путь или изменение transport snapshot |
| `event.WindowsAddress`, `event.Ncsi`, `event.Resume` и др. | Untimed путь проверен после уведомления; причины, накопленные до tick, объединены через `+` |
| `scheduled_recheck` | Проверка по существующему расписанию |
| суффикс `.settling-retry` | Уже существовавший однократный повтор после неуспеха при появлении/изменении пути |
| `captive-confirmation` | Обязательная вторая независимая проба перед автоматической авторизацией |
| `pre-step-failure` | Уже существовавшая проверка после отказа до stepOne |
| `ipc.refresh` | Явное обновление статуса через агент, например при открытии меню |
| `ipc.probe-only` | Диагностика/TXT без разрешения на автоавторизацию |
| `event.IpcCaptiveRefresh` | Явный refresh обнаружил captive и передал решение об авторизации координатору |

`start` содержит adapter ID, ifIndex, source IPv4/gateway, фиксированную контрольную
цель и бюджет. `result` — статус, `failure` (например Timeout, ConnectionFailure,
DnsUnavailable, DirectRouteUnavailable), HTTP status, общую и транспортную длительность.
`aborted` сохраняет тип исключения и длительность, после чего прежнее исключение
передаётся вызывающему коду; ошибки не подменяются успешным статусом.

Для прямого TCP-соединения **этих проб** дополнительно пишется `network.probe-tcp`:
фактический IP/порт назначения, ifIndex, источник адреса, признак кеша, результат
соединения либо Winsock-код и длительность. TCP-записи находятся между start/result
того же процесса; операции агента сериализованы существующими gates. Одно HTTP
обращение может перебрать несколько сохранённых IP. Адрес не обновляется через DNS
после ошибки. Эти TCP-записи не подключены к критическому транспорту авторизации.

Более общий HTTP-лог и записи authorization flow остаются прежними; `network.probe`
не является новым трассировщиком всех HTTP-запросов приложения. Не записываются
тела ответов, заголовки авторизации, полный URL, телефон, код или bearer.
Новые записи не отправляются в анонимную статистику. Ротация журнала остаётся прежней.

## Как считать частоту и парные пробы

Считать **start**, а не суммарное число start/TCP/result/старых `agent.path-probe`.
Для соседних start сопоставить PID, adapter, reason и предыдущий result:
так можно отличить повтор, captive confirmation, второй IPC и два события Windows.
Серия `wake` без `network.probe start` означает, что агент проснулся, но запрос не делал.

В прочитанном отрезке старого журнала одного worker за примерно 26,5 минуты были
53 строки `agent.path-probe`, из них 25 соседних интервалов короче секунды; минимум
около 0,385 с, максимум около 224,6 с. Частые/парные наблюдения подтверждены, однако
старый формат не позволяет достоверно восстановить их источники. Наличие пар само
по себе не доказывает ошибку scheduler. Для заключения нужен журнал новой сборки
при обычной работе, без искусственного переключения сети или запуска авторизации.

## Проверка изменений

Контракты подменяют сеть: coalesced WindowsAddress+Resume даёт ровно одну пробу;
untimed отказ не создаёт опрос/таймер/авторизацию, следующее событие даёт следующую
пробу. Проверяются причины, бюджет/длительность/timeout, парные start/result,
сохранность секретов, TCP cached-IP/ConnectionRefused и прежнее число dial attempts.
UI-контракты проверяют подписи и ширину столбцов 80/100/120.

Full Release подтвердил весь клиентский набор и leaderboard backend; известная
серверная ошибка ingestion на строке 142 (`2 != 0`) осталась. Следующий серверный
update-manifest контракт выполнен отдельно и прошёл. Сервер не менялся.
