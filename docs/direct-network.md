# Прямое подключение через физический адаптер (экспериментальная C#-функция)

При включённом VPN IS74Wifi может авторизовать **саму физическую сеть**, не отключая VPN для остальных программ. Это не изменение глобальной таблицы маршрутов, firewall или kill switch.

## Подключения для авторизации

Отдельных простого и продвинутого режимов нет. В `Настройки → Подключения для
авторизации` пользователь отмечает список чекбоксами. Новая установка выбирает
в списке только `Campus Wi-Fi` (существующая `SsidPolicy` включает Campus-варианты имени).
Дополнительные Wi-Fi сохраняются по точному SSID с учётом регистра, wired USB/Ethernet —
по устойчивому Windows adapter GUID, с названием для отображения. Имя профиля
«Сеть 13», текущий IP и ifIndex не являются настройкой выбора. Новый экземпляр
адаптера требует нового выбора; на похожее устройство программа не переключается.

Экран показывает текущие Wi-Fi, физические USB/Ethernet и сохранённые пункты,
включая отсутствующие устройства. `A` добавляет Wi-Fi по имени вручную (до 32 байт
UTF-8), в том числе раздачу телефона по воздуху. Пробел меняет чекбокс, Enter
сохраняет весь список, Esc отменяет черновик; в редакторе SSID Enter добавляет
имя, Esc возвращает к списку. Можно снять все чекбоксы: тогда авторизационных
сетевых запросов нет. Windows сама управляет подключением к Wi-Fi.

После завершения первоначальной настройки перечисление устройств локальное;
probe/авторизация/диагностика/обновление адресов выполняются только через выбранные
подтверждённые Windows hardware-пути. VPN,
виртуальные и не подтверждённые как hardware интерфейсы не предлагаются.
SSID/adapter GUID — разрешение проверять путь, а не доказательство captive portal.
Два независимых captive HTTP-подтверждения перед автоматическим stepOne, TLS,
polling, лимиты и расписание не изменены.

### Первоначальная настройка

Обычный первый запуск проходит пять шагов: установка (если нужна), согласие на
статистику, регистрация устройства, вопрос «Включить автоматическую авторизацию?»
и экран «Какие сети обслуживать?» с общим списком подключений.
До сохранения списка действует прежний отбор всех физических hardware-путей,
включая USB/Ethernet без Wi-Fi адаптера. Общий IP-first и исключение VPN сохраняются.
Это относится также к регистрации через CLI: список не отрезает её сетевой путь.

`initialSetupCompleted=false` обозначает незавершённую настройку. На шаге 4 поле
`initialAutomaticAuthorizationChoice` сохраняет Да/Нет, но агент не запускается.
После подтверждения списка сначала подготавливается выбранный автозапуск без
старта worker, сохраняются список и `initialSetupCompleted=true`, сбрасывается
snapshot и запускается агент уже с новым фильтром. Ответ Нет оставляет ручной запуск.
Esc в списке/закрытие процесса не завершает настройку; следующий запуск возвращает
к шагу 5 без повторного вопроса об автовходе. Пустой подтверждённый список —
завершённая настройка без разрешённых путей, не повод возвращать все сети.

В файлах прежних сборок `initialSetupCompleted` отсутствует (`null`). App определяет
его по наличию сохранённой регистрации перед созданием сетевого runtime меню/CLI
регистрации: зарегистрированным пользователям wizard не показывается; новым или
ещё не зарегистрированным предлагаются все шаги. Незавершённый явный `false` после
успешной регистрации не заменяется на `true`. Согласие и protocol/timing не меняются.

`settings.json.authorizationConnections` хранит `wifiSsids` и `adapters` (`id`, `name`).
Старые `networkMode` и `directNetworkAdapterId` читаются только для однократной
миграции и после сохранения удаляются. Simple переносится в Campus-only;
Advanced/старые настройки — в Campus плюс явно заданный адаптер, если он не
`system`. Запись adapter GUID разрешает только wired-подключение, не произвольные
SSID этого Wi-Fi адаптера. Прежнее автоматическое обслуживание всех физических
сетей больше не включается: дополнительные подключения нужно явно отметить.
Существующий новый список (включая пустой) имеет приоритет при миграции;
согласие, регистрация и интервалы не меняются.

Все выбранные подключения используют один `PathAuthorizationRunner`, один
`NetworkPathProbe` и общий `PathAddressBook`. Runner и реальные probes требуют
address book явно, DNS-first fallback конструктора нет.
`PathAddressBook` даёт connector сохранённые IPv4 без DNS в обычном запросе.
Ключ включает adapter GUID, SSID для Wi-Fi либо interface type/gateway context для
USB/Ethernet и hostname; DHCP/ifIndex не делают IP сервера устаревшим,
но новый сокет всегда получает текущую привязку интерфейса. Файл
`campus-addresses.json` отдельный от исторического `dns-cache.json` и не импортирует
его записи. Старое имя файла и Wi-Fi-ключи сохранены для совместимости с первой
установленной сборкой, исходный `CampusAddressBook` заменён общей реализацией.
Сохраняется максимум четыре адреса на сервер с происхождением DNS,
временем резолюции и успешного TCP-соединения. Запись атомарная, под межпроцессным
gate; ошибка записи не обрывает соединение. Эти адреса — кандидаты:
TCP/captive HTTP 200 не доказывают подлинность сервера. Для API сохраняются
проверка TLS-сертификата/SNI/hostname, исходный HTTP Host не заменяется IP.

Без записи используется InterfaceDnsResolver (adapter DNS, затем address-only
системный fallback). Кандидаты переиспользуются в памяти, на диск попадает адрес
после реального TCP connect. При известном IP transport timeout/Unreachable не
стирает запись и не вызывает DNS-refresh. На чистой установке с полностью
заблокированным DNS готовых IP нет: нужно получить их при доступном DNS.
Вечные IP-константы не поставляются.

Явное `Настройки → Обновить адреса серверов` обновляет активные физические пути,
отмеченные в списке. Agent получает свежий DNS трёх серверов, проверяет новый адрес через bound TCP
(и TLS с hostname для API), затем заменяет запись соответствующего host. Отказ
DNS/TCP/TLS сохраняет старую запись. Подлинность HTTP-origin портала этим не доказывается.
При частичном обновлении показывается ошибка с числом необновлённых серверов;
успешные серверы уже сохранены. Ошибка одного подключения не мешает обновить
остальные разрешённые пути. Нет stepOne/stepTwo/SMS, изменений маршрутов или
автоматической фоновой профилактики. Смена списка сбрасывает snapshot и перезапускает
установленный агент с новой настройкой.

Адреса каждого пути независимы: Wi-Fi-запись не переносится на USB. Шлюз USB
не доказывает LTE/Campus: при неизменном шлюзе сохраняются кандидаты адресов,
а состояние доступа определяется новыми HTTP-пробами. LTE-классификатора и
остановки USB после первого отказа нет. Проверки, лимиты, интервалы и backoff
остались общими и прежними; существующие сообщения о неопределённости/необходимости
действия для не-Wi-Fi пути дополнены подсказкой о возможном LTE у телефона.

### Локальная сборка для ноутбука

Аудит 2026-11-02 установил: пакеты `campus-test.1`…`.4` собраны от локальной
alpha.45 и не содержат всех исправлений актуальной GitHub `main`, несмотря на
метку `alpha.47.campus-test`. В test.5 интегрирована актуальная `origin/main`
с durable state/backup и VPN confirmation timeout; исходный аудит, результат
интеграции и синтетическое сравнение — [base-sync-audit-2026-11-02.md](base-sync-audit-2026-11-02.md).

Для установки владельцем на свои компьютеры локальная сборка имеет отдельную
метку `v0.1.0-alpha.47.campus-test.5` (выше alpha.47, ниже alpha.48). Это не релиз;
добавлены шаги первого запуска; установленные копии автоматически не заменяются.
Она может работать из canonical установленного каталога с обычным автовходом.
Перед заменой сохраняются EXE/маркер версии и локальные данные вне репозитория;
выбирается только Campus Wi-Fi, на время опыта отключается автоматическое обновление.
После установки проверяются хеш EXE, probe-only и чтение persisted IP после
перезапуска агента. Полный цикл следующей авторизации остаётся полевой проверкой.

Portable запускать с `IS74W_RUN_LOCAL=1`: CLI не переходит в установленную копию,
IPC использует одноразовый worker той же сборки. Это не sandbox: регистрация,
настройки и состояния остаются пользовательскими. До запуска выключить фоновый
автовход установленной версии и сохранить нужные локальные файлы; не запускать
install/uninstall/update. Для старой установки явно оставить в списке только Campus Wi-Fi,
получить адреса на прямом Campus с работающим DNS, затем повторить запуск без DNS
и сценарий с VPN-клиентом, оставленным включённым после потери Интернета.
Полевой цикл авторизации и ручная визуальная проверка UI ещё требуются; релиз не создаётся.
Включение автовхода из portable local-run запрещено: обычная команда включения
запускает canonical установленный EXE, который может быть старой версии. Для
проверки новой сборки использовать ручную авторизацию; успех старого агента не
засчитывается как проверка новой IP-first авторизации.

## Обслуживание выбранных путей

Программа обслуживает каждый выбранный physical path независимо. Для каждого
хранятся собственные probe/status/expiry/retry state. Раздача Wi-Fi телефона и
USB используют общий движок; заранее определять LTE/Campus у телефона не требуется.

При нескольких captive-path одновременно запускается только один SMS-flow. Приоритет
получает physical path, который Windows сообщает как текущий Internet connection profile;
остальные обслуживаются последовательно.

Состояние `Captive` перед автоматическим `stepOne` подтверждается отдельным
повторным bound HTTP-probe. Для повторной проверки выделяется минимум 2 секунды
на TCP/HTTP и при необходимости начальный DNS, включая старые настройки
`GuardProbeTimeoutMilliseconds=300`. Требование двух независимых HTTP-ответов
сохраняется. Запись `agent.path-probe-confirm` содержит failure, elapsed и budget.

Состояние авторизации читается строго, с проверенной резервной копией `.bak`,
атомарной ротацией и межпроцессной блокировкой. Повреждение без пригодного backup
и временная ошибка чтения завершаются диагностикой, а не выдуманной пустой
историей. Это отдельный механизм от IP-кеша; [контракт](path-state-durability.md).

## Общий bound TCP и первоначальный DNS

В `ApplicationRuntime` три строго выделенных клиента — API, portal и `online.susu.ru` — используют общий `PathAddressBook` и `DirectNetworkConnector`. Каждый новый **TCP**-сокет получает физический IPv4 исходного интерфейса и Windows `IP_UNICAST_IF`; `UseProxy=false`. При известном IP DNS не выполняется. При отсутствии адреса либо явном обновлении DNS A-запросы отправляются через этот же интерфейс по UDP/53 его DNS-серверам. Если прямой DNS не отвечает, разрешён **только резервный поиск адреса** через системный DNS Windows; HTTP/TLS-сокет остаётся привязанным к исходному интерфейсу. В локальном журнале виден источник адреса (`network.address`). Внутренний краткоживущий кеш InterfaceDnsResolver (30 секунд для adapter DNS, 10 для system fallback) учитывает adapter ID, ifIndex, IPv4, gateway, SSID и DNS. Он не определяет срок persistent-записи; изменение DHCP/ifIndex не вызывает скрытый DNS-refresh `PathAddressBook`. Перенаправления на посторонние домены не разрешены. HTTPS сохраняет исходное имя запроса для TLS/SNI и стандартной проверки сертификата.

Долгоживущие HTTP-соединения обновляются не реже раза в 10 секунд; новые сокеты заново выбирают доступный адаптер. После смены сетевого подключения/wake Windows существующий агент пробуждается по уведомлению ОС и пересчитывает состояние, а привязки новых сокетов берутся из текущих параметров адаптера. Ручное изменение настройки перезапускает фоновый агент.

Перед резервированием одной из четырёх автоматических попыток `stepOne` клиент делает отдельное TCP-подключение к **`w.is74.ru:80`**, действительному HTTP-порту captive portal, через выбранный адаптер. Эта проверка ничего не отправляет в captive portal. Если она не проходит, происходит обычный pre-step retry без расходования попытки. Базовый API baseline также идёт напрямую; при отказе DNS/маршрута он не расходует бюджет. Для прямого режима baseline получает максимальный тайм-аут 5 секунд вместо обычных 3, чтобы кратковременный отказ UDP DNS не прервал разрешение адреса. Если VPN/WFP блокирует прямое подключение **после** предварительной проверки, возможна обычная транспортная ошибка — абсолютной гарантии исключения гонки нет.

Прямой DNS и TCP работают только с IPv4. IPv6-адреса, возвращённые системным DNS, отбрасываются. Если системный DNS не работает либо VPN/WFP запрещает TCP вне VPN, приложение выдаёт ошибку: **fallback по HTTP/TCP не существует**. Системный DNS может использовать VPN **только для получения IP**; этот факт отображается в `network-diagnose`, и сам по себе не доказывает физический маршрут последующего TCP. Программа не изменяет правила VPN/WFP и не отключает kill switch.

## Диагностика и ограничения

После отказа TCP preflight локальный `diagnostic.log` записывает
`authorization.portal-preflight failure=dns/tcp/timeout/direct-route`, тип ошибки,
Winsock error (если есть) и длительность. Это использует уже полученный отказ,
без повторного соединения; сведения не отправляются в backend telemetry.
После неудачного timer shot agent выполняет одну bound-probe в пределах оставшегося
retry backoff, чтобы UI не сохранял старый Internet status. При Unreachable/Ambiguous
retry сохраняет свой deadline и не требует успешного captive-подтверждения этой probe.
Подтверждённый Internet на/после старой расчётной границы прекращает retry/edge-watch:
дальше путь ждёт события Windows об изменении сети или явного refresh. Периодических
HTTP probes в этом состоянии нет; если Windows не обнаружит потерю доступа,
поздний captive останется незамеченным до следующего события/refresh. Наблюдение
Internet не создаёт новый 24-часовой срок и не подменяет результат stepTwo.

`IS74Wifi.exe network-diagnose` либо `Настройки → Сеть и диагностика` просит сетевой
agent выполнить live bound-probe **каждого выбранного** активного physical path и показывает:

1. friendly name/SSID (если локальный Wi-Fi), IPv4, gateway и ifIndex;
2. какой path Windows считает preferred Internet underlay;
3. фактический статус `Internet / требуется авторизация / недоступен / неясно`;
4. сохранённую per-path ожидаемую границу и последнюю успешную авторизацию.

Диагностика не вызывает `stepOne`/`stepTwo`, не отправляет SMS и не меняет default route.
UI/CLI сам captive probe не выполняет: он отправляет agent-команду `probe-only` и после ответа
читает сохранённое per-path состояние. Обычное обновление статуса использует отдельную
agent-команду `refresh`; если agent подтверждает captive и автовход включён, дальнейшее
решение об авторизации также принимает agent. При выключенном фоне ручная команда запускает
короткоживущий agent-worker, а не возвращается к сетевой реализации внутри UI.
VPN/виртуальные интерфейсы в список authorization path не включаются. При включённом kill
switch VPN может блокировать physical packets системными правилами; в таком случае path
показывается как недоступный. При включённом kill switch VPN может блокировать физические пакеты системными правилами; в таком случае программа показывает сетевую ошибку. Привязка IP/interface не способна отменить блокирующие политики VPN и сама по себе не доказывает, через какой физический канал пакет реально вышел; это проверяется трассировкой пакетов на Windows.

Остальной трафик (`telemetry`, `updates`, `speedtest`, браузер) использует прежние независимые HTTP-клиенты/системную маршрутизацию. Никакие новые сетевые идентификаторы или DNS/IP не добавлены в удалённую телеметрию.

**Полевой тест на Windows необходим:** проверить выбранные физические пути с выключенным VPN, затем с включённым VPN (включая kill switch), переход между двумя Wi-Fi, wake/resume и обновление из обычной установки. В Linux CI доступны только статические/чистые контрактные тесты; они не подтверждают фактическую маршрутизацию WinSock или правила WFP.

### Windows 11: безопасный smoke-test перед выпуском

В PowerShell из корня репозитория (`D:\Repos\IntersvyazAutomaticWifi`), на ветке исправления:

```powershell
dotnet restore .\IS74Wifi.slnx
dotnet build .\IS74Wifi.slnx -c Release --no-restore
dotnet run --project .\tests\IS74Wifi.ContractTests\IS74Wifi.ContractTests.csproj -c Release --no-build
dotnet .\src\IS74Wifi.App\bin\Release\net10.0-windows10.0.19041.0\IS74Wifi.dll network-diagnose
```

Сначала проведите `network-diagnose` при выключенном VPN, затем с включённым (и, если применяется, с kill switch). Диагностика **не расходует попытки авторизации**, не запрашивает Bearer, не отключает VPN. В нормальном случае API вернёт `HTTP: 401`, портал — `TCP: доступен` на порту 80 и HTTP-ответ (обычно редирект). `DnsUnavailable` — не равно отказу TCP: в отчёте отдельно виден DNS fallback. Если VPN блокирует прямой маршрут, `TCP: недоступен` является ожидаемым результатом. Проверьте физический маршрут через системную трассировку/захват пакетов отдельно: успешный `curl --interface` или наш тест TCP сами по себе этого не доказывают.

Перед публикацией любых логов скройте личное имя/SSID адаптера, IPv4, DNS и сетевые идентификаторы. На сам сервер телеметрии эти сведения не добавляются.
